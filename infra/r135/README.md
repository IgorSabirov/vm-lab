# R135 Development Pipeline

**Главная точка входа — [Issue #155](https://github.com/IgorSabirov/vm-lab/issues/155).** Рабочее представление `R135 — доведение физического конвейера` находится на существующей [доске vm-lab](https://github.com/users/IgorSabirov/projects/2?query=label%3Ar135%3Adevelopment). Оно выбирает только задачи с меткой `r135:development`: главный трекер, 21 поставку и PR #159/#160. Завершённые поставки остаются видны. Видимость самой доски не меняется.

Цель — довести заявленные реализации X до проверяемого физического результата: до применимых наблюдений либо до воспроизводимого опровержения необходимого условия конкретной ветви. XA, самостоятельный XB и графовый маркер XB сохраняют отдельные выводы.

Это маршрут работ. Научные утверждения, неизвестные и решения продолжают жить в [R135](../../analysis/NOW_RESULTS_SYNTHESIS_20261106/R135.md), существующих R/U/D-реестрах. `Done`, закрытие Issue, merge и CI не присваивают им новый статус. Это сохраняет правило [#14](https://github.com/IgorSabirov/vm-lab/issues/14).

## Зависимости и параллельная работа

**28 безусловных связей** синхронизируются как GitHub `Blocked by`; **34 условные связи** остаются с явной областью в Issue и карте. Для возмущений XB входом служит микрофизика #169, а для XA — собственные взаимодействия #163. При изменении карты числа следует пересчитать, а связи проверить повторным чтением API.

Безусловная зависимость относится к приёмке результата. Например, можно заранее разрабатывать кинетический метод и проверять его на эталонах, пока физические амплитуды ещё открыты. Приёмка физической истории требует уже обоснованных входов.

Условные зависимости не превращаются в глобальные блокировки:

- Самостоятельный XB не ждёт закона графа или доказательства графового моста.
- Статический маркерный тест не требует заранее решить всю XA-космологию и не получает автоматически физических часов.
- Безразмерные SU(3)-ансамбли можно готовить до выбора масштаба в МэВ.
- Для XA нужны собственные энергия и взаимодействия; донорская микрофизика глюболов XB их не заменяет.
- Точностная нейтринная кинетика, каскад, карманы и специальные возмущения обязательны там, где этого требует физика ветви. Их отсутствие нельзя оправдать экономией времени.
- Проверенное опровержение необходимого условия освобождает ненужные последующие расчёты этой ветви. Ресурсный протокол покрывает фактически необходимые вычисления, а не искусственный полный прогон уже исключённого сценария.

Согласованные обменные процессы могут требовать совместного решения. Их физическая обратная связь не превращается в цикл обязательной очереди: отдельные поставки дают операторы/замыкания, а #175 проверяет их сопряжение.

## Приёмка поставки

Каждая Issue содержит цель, исходный SHA, входы, конкретный результат, поимённые критерии, зависимости, следующий шаг, ответственность и ограничения бюджета. Закрытие требует первичных артефактов и отдельного воспроизводимого повтора.

Доказательства оформляются файлом `infra/r135/completions/<TASK>.json` в проверенном `main`, на который указывает `completion_record` карточки. Точная схема приведена в [tools/r135_pipeline.py](../../tools/r135_pipeline.py); исполняемые примеры — в [тестах](../../tests/test_r135_pipeline.py).

Обязательны:

- точный SHA исходников и SHA-256 манифеста входов;
- файлы результата на неизменяемых commit refs с SHA-256;
- свидетельство для **каждого** критерия данной задачи;
- разные сохранённые producer/replay runs с областью, методикой, средой и результатами проверки;
- для итоговой научной приёмки — ссылка на существующее решение владельца.

Режим `provider:manifest` позволяет сохранить расчёт любой согласованной среды; `provider:github_actions` дополнительно сверяет живой run и его SHA. Нет требования переносить физический расчёт на другую площадку ради формата отчёта.

Workflow переоткрывает закрытую управляемую Issue, если отсутствует допустимая запись или не совпадают байты, входы, область и критерии повтора. Для #155 проверяется completion задачи #181. Он **не закрывает** задачи автоматически и **не выполняет** команды из Issue. Ошибка доступа к данным останавливает проверку; она не объявляется ложностью научного результата.

Эта защита проверяет наличие, структуру и целостность свидетельств. Она не может сама доказать независимость метода, истинность записанного физического вывода или волю автора решения. Поэтому квитанция явно содержит `scientific_acceptance_inferred:false` и `method_independence_proven:false`; содержательная проверка и научная приёмка сохраняются отдельно. Пока запись отсутствует, критерии не считаются выполненными.

## Состояния, ответственность и начало следующей сессии

Существующие состояния доски сохраняются: Inbox → Analysis → Ready → Running → Review → Done; Parked используется для отложенной работы. Первичный разбор назначает Ready/Analysis один раз. После заполнения `R135 block` ручные статусы и поля не перезаписываются. Актуальный head PR остаётся в `Exact source SHA`; у Issue исходный SHA — опорная ревизия её постановки.

Подготовка материалов и кода относится к исполнителю рабочей сессии. GitHub-исполнители и независимые проверяющие пока персонально не назначены; поле Assignees не содержит вымышленных назначений. Владелец принимает содержательные научные решения, а не подбирает отсутствующие коэффициенты за разработчика.

Следующая сессия:

1. Открыть #155 и выбранную Issue; проверить live HEAD связанных PR.
2. Сверить последний принятый артефакт и незакрытые критерии именно этой поставки.
3. Назвать один результат текущей работы и использовать уже существующий код/данные.
4. Опубликовать исходники, расчёт/ошибку, первичные доказательства и ограничение вывода.
5. Обновить ближайшее действие; перед закрытием предоставить проверяемый completion record.

Весь проект заново аудировать не требуется без конкретного нового изменения или противоречия.

## Автоматизация и проверка развёртывания

[Projects working board](../../.github/workflows/projects-sync.yml) запускает trusted-main обработку карты, затем существующую синхронизацию Projects. Задание `r135-pipeline` получает `issues: write` для метки, Issues и их связей, а также `pull-requests: write` для назначения той же метки связанным PR: одно право на Issues не разрешает эту операцию для PR. Отдельный Projects credential остаётся в шаге работы с доской. Код веток PR и текст задач не исполняются с этими правами.

Квитанции Actions:

- `r135-pipeline-readback/R135_PIPELINE_STATUS.json`: подзадачи, зависимости, метка, полнота и причины незакрытых доказательств;
- `projects-readback/PROJECTS_STATUS.json`: фактическое представление, поля, URL и состояния карточек.

Локальная проверка конфигурации:

```bash
python tools/r135_pipeline.py --check
python -m unittest discover -s tests -p 'test_r135_pipeline.py'
python -m unittest discover -s tests -p 'test_project_sync.py'
```

Генератор первоначальных текстов: `python tools/r135_pipeline_documents.py --out OUT`. Он не делает API-записей и не перезаписывает вручную изменённые Issues. При изменении состава обновляются карта, затронутые карточки и подтверждённые нативные связи. Избыточные ручные связи не удаляются автоматически.

Фактический результат внедрения и ссылки на квитанции следует сверять в Actions; наличие файлов или токена не считается успешным развёртыванием. Исходная точка и разбор предложений сохранены в [AUDIT.md](AUDIT.md).

## Прогресс и остаток каждого критерия

Текущее состояние открывается через [сводку #155](https://github.com/IgorSabirov/vm-lab/issues/155). Строка поставки ведёт к её Issue. У каждого критерия указаны полученное основание, проверенная область, точные артефакты, остаток, один проверяемый следующий выход и поставщики входов. Первая инвентаризация после PR #185 охватывает 86 критериев. У 29 имеется контроль, у 51 основание уровня публикации, у шести отдельное свидетельство ещё не зарегистрировано. Применение к собственной физической подготовке и приёмка по критерию на этом срезе имеют по нулю. Единица счёта — критерий; оценку человеко-часов или стоимости даёт #180 на измеренных пилотах.

### Внесение следующей поставки

1. Выбрать задачу и исходный идентификатор из `acceptance_checks` в [PIPELINE.json](PIPELINE.json). Записать ожидаемый выход в `progress.next_output`. Ближайший выход всей поставки выбирает `focus_criterion`.
2. Закрепить артефакт в Git. Для `progress_evidence` указать точный commit, путь, SHA-256 содержимого и ревизии значимых входов в `basis`. В каждый затронутый критерий добавить свой `finding` с утверждением, фактически проверенной областью, назначением `reviewed_for`, хешем проверенного требования `reviewed_criterion` и ссылками на свидетельства. Хеш даёт `criterion_digest(task, check)` из `tools/r135_progress.py`: он включает точную формулировку/ID, ключ поставки, этапы и заявленные ветви. Один файл может поддерживать разные части разных критериев.
3. Выбрать уровень по факту. `published` означает наличие описания, исходника или опубликованного результата. `control` означает проверку на обозначенном контроле. `applied` требует идентификатор собственной подготовки и полученный на ней результат. Переписать `remaining`, `next_output` и `needs`. Последние указывают задачу и нужный от неё вход. Поле `after: true` отделяет вход последующего этапа. Эти связи объясняют потребность и могут быть встречными. Безусловные зависимости приёмки задаёт отдельное поле `depends_on`.
4. При изменении принятой версии входов обновить `source_commits` или `progress_inputs`, при изменении области — `progress_target`. Изменение самого требования также делает старую привязку требующей сверки. Свидетельства сохраняют прежний текст и область; новый хеш нельзя назначать автоматически только ради восстановления уровня. Новые данные и повтор получают новую ссылку. Историю подтверждения сохраняют прежняя запись и Git. При изменении файлов вне зарегистрированных привязок исполнитель явно указывает затронутые входы. Команда сравнения показывает предыдущие и новые значения для каждого изменившегося адреса. Добавление привязок старому снимку отмечается как миграция `legacy_unbound`, без выдуманного научного повышения.
5. Статус по приёмочной записи выставляет проверка существующего протокола с артефактами, SHA-256 и двумя отдельными исполнениями (производитель и независимый replay). Для карты v2 запись и оба отчёта исполнения содержат `progress_context`: словарь ID критериев и значений `acceptance_context(plan, task, check)`. Контекст закрепляет требование, область и весь явно выбранный набор версий `source_commits`/`progress_inputs`. Поэтому прежняя приёмка не переносится автоматически на новый вход или другую постановку, даже если частичных findings не было. Актуальная приёмка проверяется независимо от старых частичных свидетельств; последние сохраняются как история. Отдельный критерий может ссылаться через `progress.criterion_record` на запись того же формата в `infra/r135/completions/`, с единственным идентификатором проверки. Для закрытия всей задачи продолжает действовать полная запись по всем исходным критериям. Научное решение остаётся у владельца.

```sh
python tools/r135_pipeline.py --check
git show d5ff18a1f4ec057ef4559705d35b5dcccd2fcd92:infra/r135/PIPELINE.json > /tmp/r135-before.json
python tools/r135_pipeline.py --check --compare /tmp/r135-before.json
python tools/r135_pipeline_documents.py --out /tmp/r135-issues
```

Последняя команда формирует сводку `progress.md` и тексты для предварительного просмотра. Проверка без сети оценивает структуру. Доверенный запуск из main отдельно проверяет содержимое закреплённых файлов, приёмочные записи, обновляет выделенный раздел каждой Issue и #155 и повторно читает результат. Прежняя ручная точка продолжения от 21 ноября сохранена в раскрывающемся разделе.

После включения этой версии в main в Projects столбец `R135 continuation` показывает актуальный критерий и ближайший выход. Синхронизация получает проверенную квитанцию `R135_PIPELINE_STATUS.json` предыдущего задания того же workflow run и делает checkout её точного SHA. До записей API проверяются репозиторий, SHA, хеш карты и полнота `criterion_completion_evidence`. Заголовок «по приёмочной записи» в редактируемом тексте Issue не является основанием пропустить критерий. Пустое `Next action`, точное прежнее значение карты или целая предыдущая автоматически подписанная строка обновляются. Ручная правка сохраняется, ожидаемое и наблюдённое значения попадают в `manual_next_action_differences` артефакта `PROJECTS_STATUS.json`. Видимый соседний столбец даёт актуальный выход и при таком расхождении. Оба поля читаются обратно после записи. При частичном отказе сохраняется отрицательная квитанция с выполненными операциями и местом остановки. Для Issues вне сопровождаемой карты остаётся прежний режим доски.

В PR проверка `R135 criterion progress` сравнивает закреплённые базу и HEAD. В артефакте `R135_CRITERION_DELTA.json` сохраняются старые и новые значения полей, изменённые пути, их потребители и предупреждения. Учитываются также удаления, оба адреса переименования, физическое дерево R135 и `RUNTIME_GATE.md`. Предупреждение привязано к конкретному источнику и его критериям: правка другой задачи, одного фокуса или служебного хеша не скрывает источник без пересмотра. Новые файлы без заявленных потребителей показываются отдельно. Это запрос содержательного рассмотрения; редакторская правка может быть объяснена без нового опыта и повышения статуса.

### Как использовать остаток при выборе работы

Уровень `control` сообщает о воспроизведённом контроле указанного фрагмента в своей области. Он не измеряет долю выполненного требования. Число потребителей входа — ориентир значимости, а не готовая очередь запуска: `needs` различает непосредственные входы, собственные входы задачи и последующие входы с `after: true`; обратные связи физических подсистем допустимы. `focus_criterion` остаётся явно выбранным следующим результатом. Его готовность определяется доступностью конкретных входов, а трудоёмкость — измерениями #180.

Для первого перехода к уровню `applied` следует сохранять один идентификатор подготовки через паспорт #161, входы #167/#168, историю #175 и результаты получателей. Само наличие строки `preparation` структурно необходимо, но не удостоверяет физическую калибровку: область применения и первичные артефакты проверяются содержательно. Отдельный успешный контроль не переносится на весь XA/XB-корпус.

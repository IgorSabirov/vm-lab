## Вывод по предложению

Первый паспорт XB — полезный следующий частичный выход #161. Его минимальная готовность означает определённую постановку, происхождение параметров и адреса открытых входов. Полная поставка MODEL продолжает охватывать XA, XB и отдельный графовый маркер. Один XB-паспорт не завершает MODEL-01…04 и не подтверждает остальные два утверждения.

Предлагаемые в отзыве разделы EOS, стенки, популяции, истории и GW нужны в паспорте как контракты. Их неизвестные значения остаются `OPEN_INPUT` с задачей-производителем. Требование сначала получить все эти результаты создало бы круг между паспортом и последующими поставками. При известном определении и неизвестной ошибке фиксируется открытая ошибка; нулевая погрешность не подставляется.

У этой оговорки есть конкретная причина в интерфейсе: `scale_from_anchor` использует sigma=0 при отсутствии поля sigma. Поэтому паспорт с открытой ошибкой нельзя автоматически превращать в готовый числовой вход простым удалением поля. Для условно фиксированного значения оси скана нулевая ошибка может быть частью определения; для неизвестной ошибки измерения требуется иной явный статус. [Реализация P1][thermo].

## Найденный дополнительный пробел: новая условная точка

Условная карта по открытому масштабу предусмотрена SCALE-04 и P1. Однако её регистрация в действующем исполнителе не завершена:

- P0 принимает роли `diagnostic`, `literature_benchmark`, `physical_candidate`.
- Общий stage-контракт допускает режим `conditional`, но исключает из него диагностические точки.
- Литературная роль сверяется с закреплёнными авторскими подготовками; изменение массы в строке не превращает её в самостоятельную точку.
- Физическая роль требует отдельных файлов калибровки и начальной истории.

Таким образом, открытый масштаб допустим как постановка исследования, но для новой собственной точки отсутствует подходящий согласованный маршрут P0/режим исполнения. Этот остаток относится к MODEL-04. Он не ограничивает аналитическую работу над условными зависимостями. [Проверка ролей P0][p0] · [Контракт исполнения][contracts] · [P1 и parameter_scan][thermo].

### Воспроизводимая проверка

[Скрипт](replay_xb_p0_contract.py) и [результат](xb_p0_contract_checks.json) фиксируют **10 проверенных случаев** на существующем коде #159. Семь первичных файлов закреплены SHA-256. Воспроизводятся реальные функции build/freeze/verify P0, проверка registry и guard роли/режима, seal и результат P0. Для изоляции этого вопроса наблюдательная таблица/правила заменены структурной фикстурой, а полный checkout/Git inventory — явно описанными заглушками. Это адресная проверка валидаторов, не полный повтор исходного P0 и не физическое моделирование.

| Случай | Результат существующего кода |
|---|---|
| Диагностическая точка, validation | Допускается |
| Та же точка, conditional | Отказ: диагностическая роль требует validation |
| Зарегистрированная FMS-точка, conditional | Допускается |
| FMS-точка, physical | Отказ: нужен независимо калиброванный physical_candidate |
| Новая роль conditional_scan | P0 отклоняет неизвестную роль |
| Масса FMS изменена с 1 до 2 ГэВ только в строке P0 | P0 отклоняет расхождение с исходными литературными параметрами |
| Seal запроса в validation с неизвестной ролью внутри registry | Запрос запечатывается |
| Затем P0 build этого registry | Неизвестная роль отклоняется |
| Успешный результат P0 на фикстуре | PASS с evidence_status=DESIGN_RECORDS |

Первый, дополнительный случай скрипта проверяет сборку всех опубликованных строк P0 с изолированными наблюдениями; поэтому в JSON десять случаев, а в таблице выше девять различающих результатов.

Повтор из этого каталога, Python 3.11+:

```sh
python replay_xb_p0_contract.py --cache /tmp/r135-xb-p0-review
python replay_xb_p0_contract.py --cache /tmp/r135-xb-p0-review --offline
```

Первая команда загружает только семь закреплённых файлов из своего репозитория. Повтор проверяет хеши до импорта. Результат записывается в `xb_p0_contract_checks.json`.

## Что удостоверяет паспорт и P0

В общем stage-интерфейсе нужно различать `seal → исполнение P0 → verify`. Seal связывает запрос с конфигурацией, входами и кодом; P0 build проверяет и создаёт записи; verify сверяет сохранённый пакет. У отдельного `p0_register.py` команды называются freeze/verify. Одного seal недостаточно: это показано отдельным отрицательным контролем.

Для `physical_candidate` P0 проверяет SHA-256/размер файлов, ID модели, истории и ветви, положительный размерный масштаб, указанный источник/ошибку и согласование параметров. Декларация независимости от BBN/CMB обязательна. Содержательная независимость калибровки, полнота физических начальных условий и корректность их значений требуют анализа первичных материалов. Статус DESIGN_RECORDS относится к регистрации постановки.

Операционная точность: `physical_launch_authorized=false` находится в [decision_rules.json][rules], а не в PLAN.json. В [PLAN.json][plan] стоят DESIGN_ONLY, execution_started=false и scientific_acceptance=owner_review. Разбор отзыва этих флагов не меняет.

## Две поверхности и две разные величины f

FMS определяет R=s_X/s_SM после конфайнмента и допускает производство энтропии во время перехода. В §III.B их f=Y/Y_eq характеризует химическую численность. [Первичный источник, §§III–III.B](https://arxiv.org/pdf/1605.08048v2).

Наши четыре литературные подготовки дополнительно используют равновесную холодную EOS при Tc минус. В `initial_history.scope` есть текст `f=1`, но формальное поле фазовой доли отсутствует. Для собственного паспорта следует раздельно определить f_conf как долю сконфайненной фазы и mu_X либо Y/Y_eq как химическое состояние. Условие равновесия и завершённость фазового превращения имеют разные определения.

Холодный эталон служит проверке дальнейшей эволюции остатка. Горячая исходная поверхность для рождения пузырей требует самостоятельного происхождения. Связь поверхностей должна учитывать энтропию и возможный обмен; R_post нельзя автоматически считать горячим начальным входом. На одной заданной равновесной поверхности R, xi и температуры связаны EOS, поэтому их совместное назначение проверяется на согласованность. [Уравнение сопоставления и ограничения][xbreadme].

## Порядок работы и минимальный следующий паспорт

Перечень шагов из отзыва полезен как порядок появления входов. Он не вводит последовательное закрытие всех Issues. EOS имеет зависимость от MODEL; безразмерные фазовые ветви можно разрабатывать при открытом абсолютном масштабе. Для гидропрофиля нужны обоснованные фазовые домены, а не искусственное продолжение стабильной таблицы ради загрузчика.

Нуклеация, нагрев, история и популяция связаны обратной связью. Для GW уже требуется сопоставление исходной и обновлённой истории с повтором источника. Односторонняя передача должна иметь оценку ошибки. Паспорт фиксирует этот контракт, а величины поставляют соответствующие задачи. [Действующая карта][pipeline] · [Источники и сопряжение #174][gwsource].

| Часть первого XB-паспорта | Проверяемый выход v0.1 | Производитель физического продолжения |

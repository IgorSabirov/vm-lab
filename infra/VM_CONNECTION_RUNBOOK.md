# VM Compute: следующее подключение после смены IP

Актуально после успешного подключения 7 ноября 2026. Начинать здесь.
Текущая ВМ: `fv4i5mtgkh5k870680fi`, адрес `158.160.159.114`,
имя HTTPS `vm-158-160-159-114.sslip.io`. Адрес динамический.
Прежние `158.160.130.220`, `81.26.188.38`, `158.160.146.58` не использовать.

**Готовый маршрут: существующий Certbot → HTTP-01 → сертификат для нового
DNS-имени и IP → deploy hook → обновление public_ip → проверка HTTPS/MCP →
новый URL в подключении ChatGPT.** Переустановка для смены IP не требуется.

## Одна команда, меняется только IP

Исходники этих команд находятся в GitHub; во время архивирования они НЕ
устанавливались в `/opt` ВМ. Использовать копию из этого репозитория.

Если пользователь уже внутри ВМ (`yc-user@compute-…:~$`), запускать **там**:

```bash
sudo python3 -I infra/reconnect_vm.py 158.160.159.114
```

Путь здесь относительно скачанной копии репозитория. Если файла на ВМ нет,
ассистент читает `infra/reconnect_vm.py` из закреплённого коммита и выдаёт
его полностью как один блок `sudo /usr/bin/python3 -I - НОВЫЙ_IP <<'VM_RECONNECT'`
с завершающей строкой `VM_RECONNECT`. Без SSH-обёртки, base64 и загрузок с ВМ.
Это тот же исходник, а не новый ремонтный скрипт.

Если пользователь на **Маке** (`ivan@Ivans-MacBook-Air ~ %`), из копии репозитория:

```bash
bash infra/reconnect_vm_from_mac.sh 158.160.159.114
```

Обёртка передаёт соседний `reconnect_vm.py` по SSH с ключом `~/.ssh/yc_key`,
выполняет его внутри ВМ и проверяет `/healthz` с Мака. ВМ не нужно скачивать
скрипт с GitHub. Новый IP задаётся единственный раз. Ни одна команда не требует
покупки статического IP. Проверка метаданных не даст применить чужой/старый IP.

После `ГОТОВО` скопировать весь напечатанный URL в подключение MCP ChatGPT.
Токен в пути остаётся прежним. Аутентификация в интерфейсе — «Без аутентификации»:
доступ ограничен секретным путём. Не публиковать этот URL или server.json.
В интерфейсе 7 ноября поле URL существующего подключения было только для чтения;
пользователь создал новое подключение. Не обещать наличие кнопки редактирования.
Ассистент завершает проверку вызовом `work_status` через новое подключение.

## Что команда действительно делает

1. Проверяет IP по метаданным ВМ и наличие именно установки `vm-compute`.
2. Приостанавливает таймер сертификата, исключает параллельный запуск команды
   и не вмешивается в уже работающий сервис продления.
3. Один раз вызывает существующий Certbot standalone HTTP-01, максимум 240 с.
   При смене IP обновляет сертификат; при том же IP сохраняет ещё действующий.
4. Вызывает существующий deploy hook, атомарно меняет только `public_ip` в JSON
   с сохранением владельца/прав. Токен и остальные настройки не меняются.
5. Перезапускает API; для worker использует `start`, а не `restart`.
   Проверяет доверие сертификату, новое имя, инструменты MCP и heartbeat worker.
6. Включает автозапуск существующих служб/таймера. При ошибке возвращает
   ранее активный таймер в активное состояние; успех не печатается.

При отказе CA конфигурация public_ip ещё не меняется. Это не транзакционный
откат всей установки: уже выпущенный сертификат и действия deploy hook после
его выдачи остаются в силе, даже если последующая проверка не прошла.
Поэтому ошибка на позднем шаге требует чтения конкретного сообщения, а не
заявления «всё восстановлено». Повтор на том же адресе не форсирует новый выпуск.
Проверка на loopback использует SNI нового имени и обычное доверие CA;
`--insecure`/отключения проверки сертификата нет. Она не заменяет проверку
внешнего подключения ChatGPT. Сигналы HUP/TERM обрабатываются; SIGKILL/отключение
питания не позволяют гарантировать завершение очистки.

## Проверенная установка — не перепутать имена

| Назначение | Путь / имя |
| --- | --- |
| API, worker, deploy hook | `/opt/vm-compute/{server,worker,deploy_cert}.py` |
| Конфигурация с токеном | `/etc/vm-compute/server.json` |
| Развёрнутый сертификат | `/etc/vm-compute/fullchain.pem`, `privkey.pem` |
| ACME lineage | `/etc/vm-compute/acme/live/vm-compute/` |
| Рабочий Certbot | `/opt/vm-compute/certbot/bin/certbot` |
| Фактическое окружение Certbot | `/opt/vm-lab/certbot` — на него ведёт симлинк |
| Версии работающего окружения | `certbot==5.8.0`, `acme==5.8.0` |
| Сервисы | `vm-compute-api.service`, `vm-compute-worker.service` |
| Продление | `vm-compute-cert-renew.service`, `vm-compute-cert-renew.timer` |
| Рабочие файлы/задания | `/var/lib/vm-compute/work/{code,data,jobs,results}` |
| Журнал Certbot | `/var/log/vm-compute-acme/letsencrypt.log` |
| Старые средства ремонта | `recover_vm_bridge.py`, Python TLS-ALPN — исторические |

**Не удалять `/opt/vm-lab/certbot`: новая установка использует его.**
Не переключать новую установку на `/etc/vm-lab/server.json` и старые сервисы.
Старая научная очередь GitHub и новый каталог work — разные части связки:
работающий MCP сам по себе не доказывает работу прежней публикации результатов.

Существующий таймер запускает `certbot renew` в 00, 08 и 16 часов UTC с небольшим
случайным сдвигом. Он обновляет срок сертификата для сохранённых идентификаторов;
смену IP и URL в ChatGPT он сам не выполняет. Сертификат от 7 ноября действует
до 13 ноября 2026; это историческая дата, следующий статус читать на ВМ.
Задания переживают разрыв SSH/чата, но не перезагрузку ВМ без собственных checkpoint.

## Когда остановиться

При `connection / Error getting validation data` не переходить автоматически
к TLS-ALPN, lego, собственному ACME-клиенту, новой ОС или очередной переустановке.
Оставить один понятный результат и уже известные факты. 7 ноября публичный HTTP
с Мака проходил, но CA не получал данные на `158.160.130.220` ни через 80,
ни через 443; после смены IP на `158.160.159.114` HTTP-01 сработал.
Точное место сетевого отказа не установлено. Это не гарантия, что любой новый
адрес заработает. Смену адреса через остановку/запуск ВМ согласовать отдельно,
если пользователь ещё не поручил её: это прерывает текущий расчёт.

Если пользователь явно требует установку с нуля, выполнить именно выбранный
им объём. Не заменять его выбор бесконечным сохранением/ремонтом. При этом
не выдавать переустановку за исправление подтверждённого сетевого отказа.

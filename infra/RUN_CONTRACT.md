# План, исполнение и квитанция

Версия 1. Область — новый запрос через legacy `github_bridge`, после отдельно проверенного развёртывания. Опубликованный исходник не означает, что действующий сервис или MCP уже обновлён. Существующие задания не останавливать, не пересоздавать и не переаттестовывать задним числом.

## Вход

`infra/run_contract.py` проверяет `vm-lab-run-plan-v1`:

- `run_id`, `source.repository`, полные `source.commit` и `source.tree_sha`;
- SHA-256 `config.json` и канонического JSON-словаря `путь → SHA-256` входов, отбираемых bridge.prepare;
- `command={entrypoint:run.py,args:[]}`;
- `authorization`: пользователь, ссылка, объём, срок (или явно постоянный);
- `budget`: прогноз, жёсткий предел времени, память MiB, диск MiB;
- `executor`: песочница при прогнозе ≤600 s, ВМ при >600 s, именованный исполнитель;
- `acceptance.required_artifacts`, `scientific_acceptance=SEPARATE_USER_REVIEW`.

Каноническая сериализация: UTF-8, `sort_keys=True`, разделители `(',', ':')`, `ensure_ascii=False`, NaN запрещён. Хеш плана не включает собственный хеш. План не помещают в коммит, чей SHA он содержит: сначала фиксируют исходники, затем отдельно публикуют план.

Очередь: `{run_id, commit, run_plan, run_plan_sha256}`. Путь плана находится внутри разрешённой рабочей директории. Одного плана недостаточно: приватный `state/authorizations/<run_id>.json` должен содержать `authority:user`, точные `run_id`, `plan_sha256`, `reference`. Это доверенная запись уже выданного разрешения, а не самосертификация автора JSON и не криптографическая подпись пользователя. Перед постановкой повторно проверяются срок, tree, конфигурация и полный входной манифест.

`verified_worker_limits` в конфигурации обязан содержать ссылку на проверку фактически работающего worker и пределы `hard_wall_seconds`, `memory_limit_mib`, `disk_limit_mib`. Нельзя заполнять его прогнозом или предполагаемыми настройками. Он аттестует ограничения внешнего worker; сам bridge не превращает эти числа в ограничения ОС. Пока конкретный worker не проверен, новый план отклоняется. Текущий MCP не объявляется совместимым автоматически.

Старые новые двухпольные запросы принимаются только при явном `allow_legacy_requests:true`; этот режим помечается `EXPLICIT_LEGACY_COMPATIBILITY` и не получает свойства нового контракта. Уже принятые записи продолжаются.

## Выход

Для новых планов bridge добавляет `RUN_PLAN.json`, `PROCESS.json`, `RESULT_MANIFEST.json` к прежнему `run.json` и файлам отчёта. Манифест содержит SHA-256 и размер каждого файла, кроме самого себя. Состояние процесса отдельно от технического гейта; автоматически устанавливается `REVIEW_REQUIRED`, `scientific_confirmation:false`. Успешный exit code не даёт научного PASS.

`python infra/run_contract.py RUN_PLAN.json --receipt RESULT_DIRECTORY` проверяет байты и идентичность. Истечение разрешения после завершения не делает историческую квитанцию невалидной. Обязательные файлы относятся к целостности квитанции: их отсутствие оставляет проверку незавершённой даже у честно опубликованного отказа. `validate_events` отдельно проверяет последовательность событий от PREPARED и запрещает тихий перезапуск после терминального состояния; автоматический сбор полного event log в текущий worker ещё не внедрён.

## Публикация и миграция

По умолчанию результаты идут в `results/<run_id>` и черновик PR. Никакого force push; повтор с тем же ID разрешён только для тех же байтов и полного того же набора файлов. Из этой публикации нельзя менять исходники и реестры. `publication_mode:legacy_main` сохранён как явно названный режим совместимости. Общий `publish_files` остаётся совместимым со старыми инженерными утилитами; это не обход научной приёмки.

Перед развёртыванием отдельно сверить конфигурацию действующего исполнителя, свободный диск, права, ограничения и текущие задания. В данной работе установщик не запускался и сервисы ВМ не менялись. Bundle установщика проверяется тестом на побайтовое совпадение с reviewed sources.

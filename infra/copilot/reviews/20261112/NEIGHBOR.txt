## 2. Что принципиально меняется в самом Copilot

С конца октября GitHub перевёл Copilot в более связанную облачную архитектуру. Теперь можно начать задачу на GitHub, продолжить её в Copilot CLI, VS Code или приложении Copilot, а затем вернуться к той же облачной сессии. Облачный агент работает в отдельной песочнице, умеет исследовать репозиторий, составлять план, менять код и создавать PR. Появилась также возможность использовать собственный компьютер или виртуальную машину как удалённую среду агента.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://github.blog\&sz=32)

GitHub Changelog+1



Для `vm-lab` это открывает четыре полезных уровня интеграции.

### А. Copilot Cloud Agent — исполнитель технических задач

Ему можно назначать GitHub Issues и поручать ограниченные изменения:

- написать тест для обнаруженного дефекта;
- реализовать адаптер внешнего проекта;
- исправить CI или упаковку результатов;
- оптимизировать алгоритм с заранее заданным критерием эквивалентности;
- подготовить PR с изменениями, тестами и объяснением ограничений.

Агент должен работать в отдельной ветке, а результат поступать через PR. Такой сценарий штатно поддерживается платными планами Copilot.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://docs.github.com\&sz=32)

GitHub Docs+1



Предлагаю: Copilot самостоятельно реализует техническую часть задачи, но не получает права объединять изменения в `main` и менять научные статусы.

### Б. Copilot Code Review — автоматический технический рецензент каждого PR

Это, вероятно, наиболее быстрая отдача от платного тарифа.

GitHub позволяет включить автоматические ревью собственных PR и повторную проверку при новых push. Уровень ревью можно выбирать по сложности:

| Уровень  | Средняя ориентировочная стоимость одного ревью | Применение в vm-lab                                         |
| -------- | ---------------------------------------------- | ----------------------------------------------------------- |
| Lite     | $0,25                                          | Документация, небольшие изменения                           |
| Balanced | $1,50                                          | Адаптеры, тесты, обычные изменения кода                     |
| Max      | $10                                            | Численное ядро, критические алгоритмы, сложные изменения CI |

Это ориентиры GitHub, а не гарантированная цена: фактический расход зависит от размера PR.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://docs.github.com\&sz=32)

GitHub Docs+1



Я бы установил Lite как обычный режим, Balanced — для исследовательского кода, Max — только по отдельному решению.

Ревью Copilot должно быть дополнительным слоем замечаний, а не обязательным научным одобрением.

### В. Agent Skills и Custom Agents — специализация под наши задачи

Это наиболее важная возможность, которой пока не хватает непосредственно в репозитории.

GitHub поддерживает специальные агенты с собственными инструкциями и ограничениями, а также навыки — воспроизводимые процедуры, которые агент загружает по мере необходимости. Они доступны в Copilot Cloud, Code Review, CLI и Copilot App.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://docs.github.com\&sz=32)

GitHub Docs+2



В `vm-lab` я предлагаю выделить пять специализированных профилей.

1\. Numerical Reviewer

Высокий приоритет

Проверяет численные методы, устойчивость, обусловленность, точность, допуски, ошибки округления, воспроизводимость и производительность.

2\. Reproducibility Auditor

Проверяет происхождение результатов: SHA, манифесты, зависимости, Docker digest, входные данные, журналы и attestation. Не принимает подпись упаковки за подтверждение самого вычисления.

3\. External Source Reviewer

Проверяет внешние статьи и репозитории, авторские версии, лицензии, соответствие контракту, различия между оригинальным кодом и нашим адаптером.

4\. Workflow Security Reviewer

Проверяет права GitHub Actions, работу с секретами, сторонние Actions, сетевой доступ, опасные команды и уязвимости цепочки зависимостей.

5\. Model Implementation Critic

Сверяет формальную спецификацию с реализацией: что задано, что вычисляется, какие инварианты сохраняются, где реализация незаметно изменила постановку.

Последний профиль может критиковать соответствие кода научной постановке, но не должен присваивать физической гипотезе статус подтверждённой. Научная приёмка остаётся за Вами.

### Г. MCP — предоставить Copilot структурированное знание vm-lab

Это, на мой взгляд, самое сильное архитектурное расширение.

Вместо того чтобы каждый раз вкладывать в запрос несколько тысяч строк реестра и документов, мы создаём небольшой специализированный MCP-сервер с типизированными инструментами чтения.

Например:

```
vm-lab MCP
│
├── registry.get_card(Rxxx)
├── registry.get_lineage(Rxxx)
├── registry.get_open_questions()
│
├── source.get_contract(IsingCauset)
├── source.compare_pinned_version(name)
│
├── evidence.get_receipt(run_id)
├── evidence.verify_manifest(path)
├── evidence.get_attestation(sha)
│
└── runtime.get_saved_status()
```

Copilot сможет спрашивать систему напрямую:

«Какие предпосылки наследует этот эксперимент?»

«Какие внешние источники используются данным адаптером?»

«Содержит ли квитанция точный SHA кода и входных данных?»

«Какие результаты затронет изменение этого контракта?»

GitHub поддерживает MCP для облачного Copilot и Code Review. Однако есть важные ограничения: облачный агент и Code Review поддерживают именно MCP-инструменты, а не ресурсы и prompts сервера; для Code Review инструменты должны явно обозначаться как read-only. Кроме того, агент, которому назначили Issue, может самостоятельно вызывать подключённые MCP-инструменты. Поэтому я рекомендую начать исключительно с чтения, без доступа к ВМ и запускам.&#x20;

Места настройки:

`vm-lab → Settings → Copilot → MCP servers`.

## 3. Самый серьёзный пробел внутри нашего репозитория

Я сопоставил текущую структуру с официальными механизмами настройки Copilot.

| Возможность                       | Состояние на текущем main |
| --------------------------------- | ------------------------- |
| `AGENTS.md`                       | Есть                      |
| `COPILOT.md`                      | Есть                      |
| `.github/copilot-instructions.md` | Не обнаружен              |
| `.github/instructions/`           | Не обнаружен              |
| `.github/agents/`                 | Не обнаружен              |
| `.github/skills/`                 | Не обнаружен              |
| `.github/hooks/`                  | Не обнаружен              |
| Репозиторный MCP для Copilot      | Не обнаружен              |

При этом `AGENTS.md` и `COPILOT.md` уже содержат наши правила, но этого недостаточно для полной нативной интеграции.

Copilot умеет загружать:

- общие инструкции из `.github/copilot-instructions.md`;
- инструкции для отдельных областей из `.github/instructions/*.instructions.md`;
- профили специализированных агентов из `.github/agents/`;
- навыки из `.github/skills/<имя>/SKILL.md`;
- hooks из `.github/hooks/*.json`.

Эти механизмы поддерживаются официальной системой настройки Copilot.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://docs.github.com\&sz=32)

GitHub Docs+4



Я бы добавил небольшую общую инструкцию и отдельные правила для `experiments/`, `analysis/`, `results/`, `infra/` и `.github/workflows/`, а не переносил весь большой `AGENTS.md` в каждый профиль.

### Что делать с Hooks

Hooks особенно интересны тем, что позволяют выполнять проверки не по просьбе модели, а автоматически в определённых точках её работы.

Для нас полезны:

- `sessionStart`: проверить ветку, SHA и чистоту рабочей области;
- `preToolUse`: остановить запрещённые инструменты и опасные операции;
- `postToolUse`: записать сведения о вызванных инструментах;
- `sessionEnd`: сохранить отчёт о сессии, изменённых файлах и итоговом SHA.

Hooks настраиваются в `.github/hooks/*.json`.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://docs.github.com\&sz=32)

GitHub Docs+1



Это не заменяет GitHub Rulesets, защиту среды и разрешения ВМ. Это дополнительный технический предохранитель.

## 4. Не заменять существующий Copilot bridge — развести два режима работы

Это принципиально важно.

Сейчас `infra/copilot_bridge.py` использует Copilot CLI 1.0.105. Он запускает отдельный процесс в пустом временном каталоге и запрещает ему shell, запись файлов, URL-инструменты и встроенные MCP.

Иными словами, он получает только тот код и текст, которые мы явно положили в запрос. Самостоятельно читать репозиторий или управлять ВМ он не может.

Это не недостаток, который нужно обязательно устранить. У этого режима есть отдельная ценность: он позволяет получить ограниченную техническую рецензию без предоставления рецензенту полного доступа к системе.

Я предлагаю сохранить два канала:

Интегрированный режим

Copilot Cloud Agent

Знает структуру репозитория, читает нужные документы, использует Skills и MCP, реализует ограниченные задачи и создаёт PR.

Изолированный режим

Copilot CLI bridge

Получает точно выбранный пакет с закреплённым SHA. Проводит отдельную ревизию без скрытого доступа к репозиторию и инструментам.

Они дополняют друг друга. Второй канал не становится независимым научным воспроизведением только потому, что вопрос отправлен отдельному процессу Copilot.

### Обновление CLI

Наш bridge закреплён на версии 1.0.105 от 30 октября. В официальных релизах сейчас обнаружены:

- 1.0.109 — стабильный релиз от 10 ноября;
- 1.0.110-3 — предварительный релиз от 12 ноября.

В 1.0.109 добавлены, в частности, новые возможности настройки сетевых ограничений песочницы и поддержка Claude Fable 5.2. [Стабильный релиз](https://github.com/github/copilot-cli/releases/tag/v1.0.109?utm_source=chatgpt.com).

Моя рекомендация — поставить 1.0.109 рядом с 1.0.105, проверить совместимость команд и флагов моста, затем провести контрольное сравнение. Старую версию пока оставить для отката. Предварительную 1.0.110-3 проверять отдельно, не переносить прямо в рабочий контур.

## 5. Самое полезное расширение: удалённая среда Copilot на отдельной ВМ

Новая функция GitHub позволяет регистрировать собственный компьютер или виртуальную машину в качестве удалённой среды Copilot через `--environment-host`.

Это открывает более интересную архитектуру, чем простая передача файлов в запрос: Copilot сможет работать в подготовленном вычислительном окружении и использовать его инструменты.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://github.blog\&sz=32)

GitHub Changelog



Но я бы не подключал напрямую основную производственную ВМ vm-lab.

Предлагаю три уровня доступа:

| Среда                   | Доступ Copilot                                                    | Назначение                                                |
| ----------------------- | ----------------------------------------------------------------- | --------------------------------------------------------- |
| Cloud sandbox           | Код, тесты, сборка, PR                                            | Основная техническая работа                               |
| Отдельная VM validation | Ограниченный пользователь, тестовая копия, разрешённые вычисления | Проверка адаптеров и воспроизведение контрольных примеров |
| Production VM           | Только через существующий авторизованный маршрут                  | Производственные научные расчёты                          |

Для отдельной VM validation нужны изолированный пользователь, отсутствие root-доступа, отсутствие производственных секретов, ограниченная файловая область и сетевой allowlist.

Для основной ВМ оставляем Ваш порядок:

`ассистент → GitHub → exact SHA → ВМ → результат → GitHub`.

Гейт времени остаётся прежним: вычисления до 600 секунд включительно — в разрешённой песочнице, свыше 600 секунд — на ВМ. Сам факт наличия удалённой среды Copilot не является разрешением производственного запуска.

Важная финансовая деталь: облачные песочницы Copilot с ноября 2026 года используют общий вычислительный бюджет GitHub Actions. Это отдельная статья расходов, не тот же самый бюджет AI Credits.&#x20;

## 6. Подключить Claude и Codex как дополнительные технические рецензенты

GitHub теперь поддерживает делегирование задач сторонним coding agents, включая Anthropic Claude и OpenAI Codex. Это публичная предварительная функциональность: агенты могут работать над задачами и создавать PR.&#x20;

Я бы использовал три последовательных уровня:

1. Copilot: основной исполнитель технической задачи.
2. Claude Code: дополнительная ревизия сложных изменений.
3. Copilot Code Review: проверка готового PR с учётом контекста репозитория и специальных навыков.

Codex можно подключать для отдельных задач, например независимого анализа алгоритма или проверки численной реализации.

При этом нужно сохранять происхождение каждого ответа. Три модели, прочитавшие один и тот же код и использовавшие одну библиотеку, не образуют три независимых научных подтверждения.

# 8. Конкретная целевая архитектура Copilot для vm-lab

Предлагаю следующую конфигурацию:

## Copilot Research Engineering System

GitHub Issues / Projects V2

Задачи, генеалогия, бюджет, критерии приёмки

Copilot Cloud Agent

Реализация кода, тесты, адаптеры, PR

Copilot Skills / Agents

Численная, техническая и доказательная специализация

vm-lab Read-only MCP

Реестр, генеалогия, контракты, квитанции, данные о происхождении

CI / Code Review

## 9. Очерёдность внедрения

Я бы реализовывал это в пять этапов.

| Этап | Что делаем                                                        | Критерий завершения                                                                      |
| ---- | ----------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| P0   | Pro+ или Pro, настройки конфиденциальности, Automatic Code Review | Copilot видит PR и выдаёт корректно оформленные ревью                                    |
| P1   | Общие инструкции, специализированные Skills и Agents              | Copilot следует научным и техническим границам vm-lab                                    |
| P2   | Read-only MCP реестра и evidence                                  | Агент самостоятельно получает проверяемые сведения о родителях, источниках и результатах |
| P3   | Hooks и ограниченная VM validation                                | Опасные действия блокируются; тестовые задачи воспроизводятся                            |
| P4   | Claude/Codex и сравнительный технический аудит                    | Измерена дополнительная польза второго и третьего рецензента                             |

### Как измерять пользу, а не количество AI-ответов

Я бы провёл первый пилот на трёх типах задач:

1. Известный программный дефект с заранее сохранённым правильным ответом.
2. Известный численный случай с точным эталонным результатом.
3. Реальная задача адаптера с заранее объявленными критериями совместимости.

Для каждого пилота измеряем:

- сколько реальных дефектов обнаружено;
- сколько ложных замечаний выдано;
- сколько замечаний удалось воспроизвести;
- сколько изменений приняли после независимой проверки;
- сколько времени и AI Credits потрачено;
- не изменились ли предпосылки, критерии и научные статусы незаметно.

Это позволит решить, окупает ли себя Pro+, нужен ли Max и есть ли смысл постоянно делегировать работу Claude и Codex.

# 10. Итоговое решение

Я вижу три наиболее ценных расширения для Вашей системы:

Первое — нативный Copilot Cloud Agent с PR. Это превратит Copilot из консультанта в исполнителя ограниченных технических задач.

Второе — MCP, Skills и специализированные агенты. Они позволят Copilot работать с реестрами, генеалогией, внешними контрактами и доказательствами, а не получать каждый раз вручную собранный фрагмент контекста.

Третье — отдельная удалённая среда проверки. Это даст более тесную связь с вычислительной инфраструктурой, но не потребует открывать Copilot доступ к производственной ВМ.

При этом существующий bridge нужно сохранить, а научное управление, изменение физических предпосылок и приёмку результатов оставить в действующей системе.

Мой выбор: Pro+ и поэтапное внедрение. Max покупать пока не нужно.

Считаю, что первым практическим пакетом изменений должны стать `.github/copilot-instructions.md`, пять Skills, четыре-пять Custom Agents, безопасный read-only MCP и автоматическое Code Review. Это создаст основу для полноценного Copilot-контура без изменения научной архитектуры.

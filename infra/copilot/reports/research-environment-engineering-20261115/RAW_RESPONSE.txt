## 1. Решение и граница MVP

**MVP — продолжить существующий `research_pipeline` и общий admission/ledger из PR #61, не создавать второй диспетчер.** Сначала наследовать PR #61 (`0c2a88268ede88909b81b04998dd91af57ddc447`) отдельным PR, затем добавить versioned контракт эксперимента, два адаптера — конечный ADD F2 и Serbian `SignatureKernel` — и общий маршрут до независимой проверки и draft PR. #61 не находится в активной опорной ветке: его исправления допуска и маршрутизации здесь **не считаются развёрнутыми**. Не трогать активные `CONTROL`, `RUN_REQUEST`, `CURRENT`, persistent webhook и научные статусы.

Один пакет содержит обе независимые секции с общими `package_id`, матрицей, source SHA и пререгистрированными критериями. Совместное исполнение проверяет только инженерную среду; **оно не устанавливает физическую связь ADD с гравитацией**. Остальные направления остаются записями возможностей в существующих `SOURCE_INDEX` и `infra/external/contracts`; никакого выдуманного `READY`.

Experiment contract — versioned JSON, а не разрешение исполнять команды из него. До admission он фиксирует: `package_id/revision`; неизменяемые `source.commit/tree_sha`; пины каждого backend; manifest SHA-256 входов; вопрос и родителей; матрицу `task_id/seed/adapter`; observable contract (имя, смысл, единицы, модельный шаг/порядок событий, мера или `NOT_DEFINED`, интервенции); predeclared controls/criteria и версию verifier; разбиение на **независимые целые** секции; бюджет package/section/process/job/VM и предварительную калибровку. Каждая секция несёт provenance адаптера и lock/image digest. Для MVP задаются явно: ADD — `time_index` как индекс модельного шага, не физические часы; Serbian — пачка симметричных матриц, результат `inertia=(positive, negative, zero)`, не время. Общего `z=(G,Q,M,A,R,C)` нет.

**Не установлены в переданных данных** подходящие калибровки и digest образов для нового маршрута. Их нельзя заменить историческим timing чужой задачи, версией runner label или вымышленным хешем: preflight обязан отказать до вычислений, пока фиксированные environment lock/digest и калибровка не приложены. Использовать утверждённые лимиты, не увеличивая память/выходы: 4 GiB и 2 GiB из `CONTROL` PR #61; один активный пакет, не более одного нового на событие и двух за скользящие 24 часа.

## 4. Контракт и примеры

Минимальные методы нужны для регистрации возможностей и полного прохождения пакета. Не поддерживаемое действие возвращает явное `UNSUPPORTED`/`NOT_IMPLEMENTED`, не нулевое наблюдение. Все адаптеры остаются изолированными и владеют собственными параметрами и состоянием.

**Предлагаемый код — UNEXECUTED:**

```python
from typing import Protocol, TypedDict, Literal

Status = Literal["OK", "UNSUPPORTED", "NOT_IMPLEMENTED", "FAIL"]

class Receipt(TypedDict):
    status: Status
    artifacts: list[str]
    provenance: dict[str, str]

class Adapter(Protocol):
    def describe(self) -> dict: ...
    def prepare(self, job: dict, workdir: str) -> Receipt: ...
    def calibrate(self, job: dict, environment: dict) -> dict: ...
    def run(self, job: dict, workdir: str, deadline_utc: str) -> Receipt: ...
    def extract(self, job: dict, workdir: str) -> Receipt: ...
    def verify(self, job: dict, workdir: str) -> Receipt: ...
```

`describe()` перечисляет поддерживаемые операции и контракт observable. `prepare()` проверяет входы/пины и фиксирует подготовленное состояние; `calibrate()` только записывает измерение для выбора маршрута; `run()` выполняет одну заранее разрешённую секцию; `extract()` формирует raw/summary/manifest; `verify()` независимо пересчитывает hash/полноту/предъявленные controls, не меняя scientific acceptance. Если операция не реализована, например продолжение/checkpoint, adapter указывает `NOT_IMPLEMENTED`; controller не подменяет это пустым результатом.

## 5. Очередь, исполнение и надёжность

**Статусы исполнения**: `DRAFT → READY → BUDGET_WAIT | RESERVED → SUBMITTED → QUEUED → RUNNING → VERIFYING → COMPUTE_COMPLETE → PUBLISHED`. Ошибка секции даёт `PARTIAL` или `FAILED`, не стирая успешные секции. Параллельные оси: evidence `COMPLETE/INCOMPLETE/INVALID`, численный вывод `CONTROL_PASS/FAIL/NOT_EVALUABLE`, научная приёмка `false/REVIEW/ACCEPTED` — только решение владельца. `COMPLETE` нельзя выставить, пока обязательные процессы завершились, полная матрица покрыта без дублей и независимый verifier подтвердил доказательства.

- Idempotency key: `(package_id, section_id, source_sha, plan_sha256)`. Перед submit все исполнители проходят один admission и один ledger CAS. Повтор события видит существующую reservation/result и не запускает науку повторно; CAS conflict означает перечитать ledger и снова решить. Неопределённый ответ записи/submit означает сверить live Actions/VM, не повторять запрос.
- Новый пакет маршрутизируется по **предварительной применимой калибровке**: целиком до 600 секунд включительно — local; независимые целые секции длиннее — Actions, каждая не более 6 часов **с подготовкой, верификацией и выгрузкой**; непрерывная задача, которая с запасом не укладывается в job, — ВМ по GitHub на фиксированном SHA. Одна траектория не дробится. Различать package sum, section wall, process, Actions job и VM budgets; ограничения `memory/output` и единая группа конкуренции PR #61 сохраняются.
- Не допускать двух диспетчеров: после наследования PR #61 вычислительное решение остаётся в `research_pipeline`/общем admission. Новый scheduled workflow на default branch — **только сигнал пробуждения** существующему controller, не второй runner и не источник исполнения; он не вызывает LLM. Controller повторно читает `not_before`, readiness, активный ledger и live inflight, затем проходит тот же CAS. До `not_before` — no-op; после окна допускается только готовый пакет. Расписание может задержаться и не обещает запуск в точную секунду.
- Скользящее окно объединяет local, Actions и VM через ledger; незарегистрированные live Actions учитываются консервативно. Ровно в момент истечения старейшего из двух reservations пересчитывается окно по правилу `started_utc > now - 24h`, но активная reservation блокирует новый пакет независимо от возраста. Лимиты — не более одного нового пакета на событие, двух за 24 часа, одновременно одного вычислительного пакета.
- Сбой секции сохраняет её failure receipt и raw другой секции; без обязательной секции агрегатор ставит `PARTIAL/FAIL`. **Научного retry нет.** Publisher после `COMPUTE_COMPLETE` может восстановить публикацию из сохранённого проверенного bundle; это не повторная reservation/научный запуск. Ledger хранит отдельно compute-terminal и `publication_pending`, чтобы публикационный сбой не выдавался за новый вычислительный результат и не переписывал первую квитанцию.
- Публиковать только после независимой проверки. Версионированная папка результата неизменяема; новый result не заменяет прошлый. `CURRENT.json` — только указатель на последний полностью проверенный опубликованный bundle, не статусный реестр. В одном Git commit создать новую папку и обновить pointer; branch ref обновляется fast-forward, без force. Повтор publisher использует тот же publication key и hashes: существующая ветка должна совпадать по дереву и родителю, иначе остановка с ошибкой. Проверить commit/tree, manifest hashes и наличие draft PR. Publisher публикует draft, не merge; изменение научных статусов запрещено.
- При изменении HEAD после freeze `source_check` отвергает запуск; публикационный commit сохраняет исходный SHA эксперимента. Если публикация не удалась после расчёта, workflow сохраняет bundle как Actions artifact и запускает только фиксированный recovery mode для уже проверенного bundle. Дубли событий и смена HEAD не легитимизируют новый расчёт.

Общий API не даёт сопоставимости. Для сравнения нужна заранее заданная семантика observable, единиц, времени/порядка, меры и интервенций. Для физической композиции требуется отдельное явное отображение выход→вход с областью применимости и проверкой нужных сохраняемых наблюдаемых/динамики. Coarse-graining допустим, если заявлены и проверены его условия; биекция не обязательна. Хассе/замыкание не переносить на ADD или R129 без заданных носителя и `K`. Не вводить общий инвариант, меру, закон S2, сектор X или мост BH1. Стандартный S3 не зависит от neutt/BH1.

## 7. Ограничения и основные риски

Нет полного author solver для CCC+TL/Anthropic и нет исполнимых ансамблей IsingCauset/CDT; общая оболочка этого не исправляет. Исторический Serbian отчёт не является доказательством нового маршрута. ADD smoke — наша реконструкция конечного F2-варианта, не аттестация авторского закона. Активные исходники и очередь не изменены; сборка, тесты, публикация и C++ **не выполнялись**.

Главные риски: (1) неподходящая калибровка или плавающая среда даст неверный маршрут — закрывать фактическим lock/digest и измерением до допуска; (2) гонка между CAS, live Actions и внешним VM/local исполнителем — один shared ledger и консервативная reservation при неопределённости; (3) публикация частичного bundle может создать ложное `COMPLETE` — независимая полнота секций до атомарного commit/pointer и отдельный recover-only publisher.

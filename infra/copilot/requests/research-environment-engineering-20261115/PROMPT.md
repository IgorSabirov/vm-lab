# Copilot: инженерный проект единой среды исследований vm-lab

Поручение владельца: «Сформируй запрос и отправь Копилоту». Предыдущий обзор — issue #58 / PR #62. Теперь нужен конкретный инженерный проект и предлагаемый код первого вертикального среза, пригодные для реализации в нашем репозитории. Ты отвечаешь за архитектуру, интерфейсы, исполнение, надёжность и тесты. Научную постановку и физические мосты определяем отдельно; не повторяй научное эссе из PR #62.

## Главный вопрос и результат

Как превратить уже имеющиеся шесть направлений в нашу модульную вычислительную среду внутри IgorSabirov/vm-lab, где разрешённые исследования автоматически проходят полный путь от закреплённой постановки до проверенного опубликованного результата?

Нужен один минимальный реализуемый проект: расширение существующего контроллера, единый контракт адаптеров, две реальные интеграции Python + C++, точные файлы/функции для изменения и проверяемая приёмка. Остальные направления — честные записи возможностей и зависимостей, без фиктивной готовности. Не проектируй новую платформу рядом с рабочей.

Режим этого запроса — один текстовый инженерный ответ. Инструменты у модели выключены. Переданные исходники доступны полностью там, где указан FULL_TEXT; ссылки сами по себе не означают чтения. Ты можешь предложить код/патч, но не утверждай, что изменил репозиторий, собрал C++ или выполнил тесты. Ответ доверенный publisher сохранит в draft PR; его код ещё предстоит независимо применить и проверить. Не имитируй результаты исполнения.

## Источники и исходная архитектура

Предложи наследование этой работы отдельным PR; не переписывай её заново и не называй уже развёрнутой.

Использовать и расширить:
- infra/research_pipeline.py: DAG, allowlist IMPLEMENTATIONS, исполнение и проверка импортированных свидетельств; сейчас PKG привязан к CCC, реализации s1_fullnet/s_eta.
- infra/autonomy/{admit.py,execution_policy.py,finish.py,LEDGER.json,CONTROL.json} из PR #61: единый бюджет, CAS-резервации и закрытие исполнения.
- infra/run_contract.py, infra/RUN_CONTRACT.md, существующие publisher/verifier, SOURCE_INDEX и infra/external/contracts; не создавать конкурирующие реестры статусов.
- Существующие Python ADD и C++ signature_kernel/build_and_check как первые две инженерные интеграции. Их совместный запуск доказывает работоспособность среды, а НЕ физическую связь ADD с гравитацией.

Шесть направлений: CCC+TL; Anthropic; Serbian piecewise-flat QG; IsingCauset; CDT2D; ADD. Это не шесть одинаково готовых репозиториев. CCC_SPARC — только часть CCC, а не BBN-движок. Anthropic представлен публикациями и нашими редуцированными проверками, не авторским полноценным solver. ADD — наши явные варианты реализации, без аттестации авторского кода. У Serbian уже есть архив, C ABI и Python-обёртка. IsingCauset/CDT пока не превращать в READY без исполнимого контракта. Все pins, происхождение и лицензии брать из переданных источников.

## Требуемая конструкция

1. **Один общий контракт, изолированные движки.** Предложи versioned schema/Protocol для describe/capabilities, prepare, calibrate, run, extract, verify. Конкретизируй минимально нужные операции: не создавай абстракции без потребителя. Параметры, зависимости и native state каждого движка остаются своими. Отсутствующая возможность — явный UNSUPPORTED/NOT_IMPLEMENTED, не нулевое наблюдение. Нужны единицы, смысл времени/порядка, мера и допустимые интервенции, provenance, environment lock/image digest. Никакой принудительной общей физики z=(G,Q,M,A,R,C).

2. **Контракт эксперимента.** package_id, revision, source SHA, pins, input hashes, seed/task matrix, вопрос и родители, observables, controls, критерии до исполнения, бюджет и оценка времени, разбиение на независимые секции, версия verifier. Научные пороги не подбирать по результатам. Отдельные статусы инженерного выполнения, полноты доказательств, численного вывода и научной приёмки.

3. **Два реальных адаптера.** Для Python ADD выбери конкретные существующие функции и явно назови вариант оператора; не выдавай smoke-скрипт за аттестацию закона или полный ансамбль. Для Serbian переиспользуй SignatureKernel и закреплённый C++ архив/сборку, сохрани лицензии. Опиши минимальные входы, команды, выходы, verifier и статусы. Существующие результаты переиспользовать; новые малые инженерные проверки должны проверять именно новый адаптер/маршрут. Не запускать весь исторический научный пакет ради демонстрации общей оболочки.

4. **Единая очередь и маршруты.** Расширь имеющуюся allowlist вместо динамического исполнения команд из Issue/PR/JSON. Один логический пакет может содержать несколько независимых jobs/секций с одним package_id, общей матрицей и неизменным source SHA. <=600 секунд на весь вычислительный пакет — локальная среда; более длинные независимые секции — Actions, максимум 6 часов на job вместе с подготовкой/выгрузкой и запасом; непрерывная интеграция, не помещающаяся в job, — ВМ через GitHub и фиксированный SHA. Не дробить одну траекторию искусственно. Бюджеты package/section/process/job/VM различать. Сохранить действующие лимиты числа пакетов, памяти/выходов и единую группу вычислительной конкуренции; не повышать их в обход владельца. Расчёт стоимости/времени — по реальной предварительной калибровке, не по чужому ноутбуку.

5. **Надёжность и пробуждение.** Использовать ledger + Actions/VM receipts, idempotency key и CAS-reservation. Дубли событий, смена HEAD, сбой публикации и повторный webhook не запускают научный прогон повторно. Секция FAIL не исчезает и не заменяется удачной выборкой. Если без отсутствующей секции нельзя вынести результат, пакет PARTIAL/FAIL; автоматического научного retry нет. Publisher допускает восстановление публикации из уже сохранённых артефактов без нового расчёта. Запланированное пробуждение очереди на default branch повторно проверяет not_before, readiness, inflight и бюджет. Schedule может задержаться; он не гарантирует запуск точно в назначенную секунду. Объясни миграцию, чтобы не было двух диспетчеров и двойного запуска. Проверка очереди не должна каждый раз вызывать LLM.

6. **Результаты.** Единый конверт raw artifacts + SUMMARY + ARTIFACTS manifest + hashes + environment + resource facts + verifier receipt + source/run/section lineage. Терминальный COMPLETE разрешён только после завершения всех нужных процессов/секций и проверки полноты. Научный FAIL/REVIEW сохраняется даже при ENGINEERING_PASS. Отдельно укажи, где и как атомарно обновляется текущий указатель, как сохраняется прошлый и как проверяется публикация.

7. **Сопоставимость и физическая композиция.** Общий API сам по себе не разрешает сравнивать величины. Для сравнения нужен observable contract; для связи модулей — явное отображение выход→вход, единицы, область применимости и проверка сохранения нужных наблюдаемых/динамики. Биекция не обязательна: coarse-graining допустим при заявленных и проверяемых условиях. Хассе/замыкание не применять к ADD или R129 без определённого отображения носителя и K. Не придумывать общий инвариант, меру, закон S2, сектор X или мост BH1. Стандартный S3 не зависит от neutt/BH1.

## Приёмка предлагаемого MVP

Дай таблицу конкретных тестов (вход → ожидаемый исход → артефакт), как минимум:
- оба адаптера проходят один и тот же lifecycle и оставляют независимые raw/manifest/verifier receipts;
- неверный pin/hash, неизвестный adapter и UNSUPPORTED отвергаются до выполнения;
- повторный event и конкурирующие запросы не дублируют reservation/job;
- скользящий лимит учитывает local + Actions + VM, в том числе границу истечения одного из двух пакетов;
- сбой одной секции сохраняет результат другой, не публикует ложный COMPLETE и не перезапускает науку;
- после успешного расчёта сбой publisher восстанавливается без нового исполнения;
- пробуждение до not_before не запускает, после окна допускает только готовый пакет, а действующий inflight блокирует повтор;
- полная цепь plan → admission → run → raw → independent verifier → draft publication сохраняет source SHA и scientific_acceptance=false.

Не надо требовать нового согласия владельца перед каждым уже разрешённым готовым этапом. Смена научной цели, меры, закона или носителя требует отдельного решения; обычную реализацию и исправления в согласованном объёме контроллер доводит до запуска. Научный приёмщик — владелец; зелёный CI не меняет R/C/L/U. Активные исходники/CONTROL/RUN_REQUEST/CURRENT и persistent webhook сейчас не менять, научные PR автоматически не сливать.

# Поддержание связей и происхождения реестров

Научные утверждения хранятся в исходных карточках. Инфраструктура обеспечивает типизацию, навигацию, проверку происхождения файлов и согласованность производных представлений. [Директива разделения науки и инфраструктуры](../SCIENCE_INFRASTRUCTURE_SEPARATION.md).

## Источники истины

- `analysis/NOW_RESULTS_SYNTHESIS_20261106/RESULTS_REGISTER.json`: R/C/L, научные поля, родители, прямые предпосылки и связи.
- `analysis/NOW_RESULTS_SYNTHESIS_20261106/OPEN_QUESTIONS.json`: U и их научные статусы.
- `analysis/FOUNDATIONS_LITERATURE_20261103/PREMISES_CURRENT.md`: 66 условий A01–G08 и девять отдельных N-долгов.
- `analysis/REGISTRY_LINKS/SOURCE_PINS.json`: явные хеши файлов, объявленных как managed sources.

Не редактировать производные индексы вручную.

## Типы и связи

Типы узлов различаются: `result:R001`, `construct:C001`, `link:L01`, `question:U010`, `premise:B03`, `obligation:N02`.

- `parent`: генеалогия результатов.
- `addresses`: отношение результата к конструкции.
- `direct_conditional_evidence`: явно указанное условное свидетельство по предпосылке.
- `historical_navigation_not_proof`: историческая навигация через конструкцию.
- `informs_not_closes`: результат связан с открытым вопросом, но не закрывает его.
- `contextual_reference_not_closure`: N-долг ссылается на результат как на контекст; ссылка не означает закрытие долга.
- `boundary_open`: открытая граница сохраняется.

N01–N09 не переводятся в узлы premise: это отдельные долги второго реестра. N03 сохраняет статус CONDITIONALLY_RESOLVED, остальные статусы извлекаются только из текста-источника. Условия закрытия не изобретаются компилятором; если их нет в исходнике, это прямо помечается.

Исторические литературные L01–L71 не являются открытыми проектными L01–L10.

## Глубокая навигация

Компилятор создаёт устойчивые HTML-якоря для R/C/L, U, 66 premise-строк и N01–N09. Узлы графа хранят `path`, `anchor` и `target`, поэтому индекс ведёт к записи, а не только к началу большого файла.

Старые ссылки на карточки сохраняются; новые ссылки используют пространства имён, например `#result-r129`, `#question-u010`, `#premise-b03`, `#obligation-n02`.

## Происхождение источников

`SOURCE_PINS.json` — исходный baseline для файлов, перечисленных в `results[].managed_sources`. Для каждого файла закреплены:

- путь;
- Git blob SHA;
- SHA-256;
- роль источника;
- фрагмент/якорь, если он был явно выбран;
- ID результатов, которые ссылаются на него.

`SOURCE_PROVENANCE.json` — генерируемая квитанция сверки этих пинов с текущим содержимым. Хеш удостоверяет идентичность файла, но не доказывает, что каждое утверждение внутри него поддерживает связанную научную формулировку.

Если managed source изменился, обычная проверка завершается ошибкой. После просмотра diff и принятия новой редакции пины можно обновить явно:

```bash
python tools/registry_links.py --refresh-source-pins --write
python tools/registry_links.py
python -m unittest discover -s tests -p test_registry_links.py
```

Не применять `--refresh-source-pins` автоматически в CI: изменение источника требует человеческого рассмотрения. Для обычной перестройки уже подтверждённых данных достаточно `python tools/registry_links.py --write`.

## Производные файлы

Компилятор поддерживает:

- `analysis/REGISTRY_LINKS/INDEX.json` и `INDEX.md`;
- `analysis/REGISTRY_LINKS/SOURCE_PROVENANCE.json`;
- `analysis/FOUNDATIONS_LITERATURE_20261103/PREMISES_CURRENT.json`;
- `analysis/FOUNDATIONS_LITERATURE_20261103/N_DEBTS.json`;
- устойчивые якоря в Markdown исходных реестров;
- карточки с `managed_card: true`.

Источники истины остаются Markdown/JSON исходных реестров и SOURCE_PINS. Генератор не создаёт научные связи по совпадению слов, не выбирает субстрат, не выводит физическую архитектуру и не повышает статусы.

## Обычный цикл обновления

1. Изменить исходную карточку с её свидетельствами, условиями и границами.
2. В новой R-карточке явно объявить родителей, конструкции, вопросы, предпосылки и managed sources.
3. Если файл является управляемым свидетельством, добавить его в SOURCE_PINS осознанно; при изменении уже закреплённого файла сначала просмотреть diff.
4. Выполнить `python tools/registry_links.py --write`.
5. Выполнить `python tools/registry_links.py` и тесты.
6. Опубликовать исходники и производные файлы в одном логическом PR.

## GitHub Actions

Workflow `.github/workflows/registry-links.yml` проверяет детерминированную сборку и тесты при относящихся к реестру push/pull_request и вручную. У workflow минимальные `contents: read`, отключённые checkout credentials, закреплённый SHA action, лимит времени и concurrency cancellation.

CI не записывает изменения обратно, не запускает научные расчёты/ВМ, не вызывает внешнего ИИ и не меняет научные статусы. При расхождении он показывает устаревшие файлы и завершается ошибкой; автор обновляет производные файлы и проверяет diff.

Текущая область provenance ограничена managed sources, объявленными карточками. Она не означает полного хеширования всех исторических архивов и внешних URL. Граф подтверждает существование и типизацию объявленных связей, не истинность научных утверждений.

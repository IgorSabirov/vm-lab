# Поддержание связей двух реестров

Научные выводы хранятся в существующих карточках, инфраструктура здесь отвечает только за их согласованность и навигацию. [Директива разделения](../SCIENCE_INFRASTRUCTURE_SEPARATION.md).

## Источники истины

- `analysis/NOW_RESULTS_SYNTHESIS_20261106/RESULTS_REGISTER.json`: R/C/L, родители, типизированные связи. Старые карточки Markdown сохраняются; новые карточки с `managed_card: true` генерируются из JSON в помеченных блоках.
- `analysis/NOW_RESULTS_SYNTHESIS_20261106/OPEN_QUESTIONS.json`: U и их научные статусы.
- `analysis/FOUNDATIONS_LITERATURE_20261103/PREMISES_CURRENT.md`: 66 исторических условий и девять дополнительных N-долгов. Машинное зеркало создаётся автоматически из текста, а не редактируется отдельно.

`legacy_crosswalk` уже сопоставляет все 66 условий с конструкциями. Скрипт использует это существующее сопоставление, чтобы не создавать второй ручной список. Новые прямые связи задаются явно в `results[].premise_ids`. Историческая навигация через конструкцию и прямое адресное свидетельство — разные типы рёбер.

Имена типизированы: `premise:C01`, `construct:C001`, `result:R001`, `question:U010`, `link:L01`. Литературные L01–L71 в прозе второго реестра не распознаются как открытые связи проекта. По совпадению слов и похожим ID научные связи не создаются.

## Обычное обновление

1. Изменить исходную карточку с её свидетельствами, границами и научным статусом; человеческое решение о статусе остаётся обязательным.
2. В новой R-карточке объявить родителей, конструкции, вопросы и адресные предпосылки; источники новой управляемой карточки перечислить также в `managed_sources` для проверки существования.
3. Выполнить `python tools/registry_links.py --write`.
4. Выполнить `python tools/registry_links.py` и `python -m unittest discover -s tests -p test_registry_links.py`.
5. Опубликовать исходники и производные файлы одним коммитом. Не редактировать INDEX.json/INDEX.md и PREMISES_CURRENT.json вручную.

Скрипт формирует двустороннюю [карту](../analysis/REGISTRY_LINKS/INDEX.md), её JSON, машинное зеркало предпосылок и управляемые новые R-карточки. Проверяет уникальность ID, разрешимость типизированных ссылок, полное покрытие 66 условий, наличие R/C в Markdown, существование объявленных источников и совпадение управляемых карточек. Для R122 отдельно защищено согласование исправленной границы о нерассчитанном интервале после шестого деления.

## GitHub Actions

Workflow `.github/workflows/registry-links.yml` запускает те же проверки при относящихся к реестрам push/pull_request и по ручному workflow_dispatch. Только Python standard library, checkout закреплён SHA, доступ `contents: read`, предел задания 3 минуты, повторный устаревший запуск отменяется.

Проверка ничего не публикует сама, не запускает научные расчёты/ВМ, не обращается к внешнему ИИ и не меняет научные статусы. При расхождении она показывает устаревшие файлы и завершается ошибкой; автор запускает `--write` и проверяет изменения. Сводка помещается в GitHub job summary. Это автоматизация детерминированной работы, не дополнительный научный гейт.

Текущее покрытие не означает проверки всех исторических внешних URL или полной смысловой эквивалентности старых текстов R/C/L. Граф устанавливает существование объявленных связей, не истинность выводов. Старые источники в других SHA не загружаются на каждом CI-запуске.

## Внешние разборы и обратная навигация, 12 ноября 2026

В `RESULTS_REGISTER.json → external_reviews` хранится одно явное решение о каждом новом сопоставлении. Разбор получает пространство имён `review:…`, а не новый R-номер. Каждая положительная связь содержит `target`, `relation`, `rationale`, `claim` и `evidence` с якорем раздела. Отдельный `excluded_links` сохраняет отклонённые или нерелевантные сопоставления с причинами; в положительные рёбра они не попадают.

Разрешённые отношения внешнего разбора: `scope_boundary`, `operational_requirement`, `clock_comparison`, `joint_model_requirement`, `conditional_open_system_constraint`, `classification_only`, `time_scale_analogy`, `premise_context_not_evidence`. Ни одно не означает нового физического свидетельства. Для подтверждённого результата применяется обычная R-карточка с собственной областью доказательства; инфраструктура не выбирает её статус.

Генератор автоматически:

- строит входящие и исходящие переходы для каждой R/C/L/U/предпосылки/разбора с устойчивыми типизированными якорями в INDEX.md;
- добавляет обратную ссылку непосредственно в затронутые R/C/U-карточки и таблицы внешних разборов в оба реестра;
- отражает контекстные ссылки в `PREMISES_CURRENT.json → context_review_ids`, отдельно от `direct_result_ids`;
- проверяет существование и тип адресата, смысловой тип связи, наличие обоснования и якоря свидетельства, противоречие между включёнными/отклонёнными ссылками;
- учитывает SHA-256 управляемых файлов разбора: изменение свидетельства делает старый INDEX.json устаревшим.

Производная секция `generated:external-review-links` в PREMISES_CURRENT.md исключается из хеша семантического входа перед генерацией. Поэтому обратная ссылка не создаёт цикл «зеркало меняет собственный источник». Основные 66 строк и девять N-долгов остаются ручным научным источником. Идемпотентность проверяется тестом.

Примеры адресного поиска без чтения всего реестра:

```sh
python tools/registry_links.py --node question:U006
python tools/registry_links.py --node premise:B06
python tools/registry_links.py --node review:CCC_TL_20261112
```

Один набор явных рёбер используется для Markdown, JSON и CLI. Не поддерживать второй ручной список обратных ссылок. GitHub Actions проверяет синхронность при изменениях `analysis/**`, генератора, тестов и этого порядка ведения. Он не запускает `verify_algebra.py`: проверка научной алгебры и инфраструктурная CI имеют разные назначения.

## 3. Самые важные разрывы в автоматизации

### А. CI не проверяет весь исполняемый код проекта

В текущем `main` workflow выполняет две команды:

```
python3 tools/registry_links.py --summary "$GITHUB_STEP_SUMMARY"
python3 -m unittest discover -s tests -p test_registry_links.py
```

То есть он проверяет компилятор реестра и его собственные тесты. Он не запускает остальные тестовые наборы инфраструктуры, X27, NOW и E002.

В активной части дерева нашлось 32 файла тестов. Ещё 45 файлов с похожими именами находятся внутри архивных VM-снимков в `results/`; это не действующие тестовые наборы, и автоматически запускать их не нужно.

Это важнее, чем просто «добавить ещё один workflow». Нам нужна матрица проверок по типам изменённого кода, чтобы изменение моста не оставалось без тестов, а изменение научной фикстуры не запускало весь архив.

### Б. Исполнитель и публикация результатов не согласованы с будущей защитой `main`

В `infra/github_bridge.py` сейчас реализовано следующее:

1. Мост обнаруживает заявку из `data/vm_lab_queue`.
2. Получает конкретный Git commit и проверяет его SHA.
3. Отбирает разрешённые исходные файлы, ограничивает размер, запрещает symlinks и submodules.
4. Передаёт пакет вычислительному worker.
5. Проверяет выходы и сохраняет их контрольные суммы.
6. Формирует commit с результатами и отправляет его непосредственно в `refs/heads/main`.

Это уже серьёзная инженерная работа. Но шестой шаг конфликтует с архитектурой защищённой основной ветки.

Если включить обязательные PR для `main`, прямой push моста перестанет работать. Если оставить прямой push, серверная защита не будет обеспечивать требуемый порядок интеграции.

Ещё одна граница: `discover()` принимает заявку с двумя полями — `run_id` и `commit`. В самом формате заявки нет ссылки на явное разрешение пользователя, предельный бюджет, срок действия разрешения и подтверждение того, что именно этот пакет разрешено исполнить.

Возможно, действующий рабочий процесс обеспечивает это внешним контролем. Но сам мост этого не удостоверяет. Это нужно исправить в контракте запуска, не меняя научную методику и не нарушая уже действующие задания.

### В. Два маршрута исполнения пока не образуют один контур

В репозитории одновременно присутствуют:

- `github_bridge.py` — старый файловый мост, очередь, worker и собственная публикация;
- `github_result_reader.py` — чтение результатов только с фиксированного Git commit;
- `launch_control.py` — локальная проверка квитанций, упаковка, прогноз и сверка;
- текущий MCP-маршрут `VM Compute 81`.

Сам `CURRENT_RUN.json` прямо предупреждает, что старый bridge и новый MCP — разные маршруты, а наличие кода моста не подтверждает, что его служба сейчас работает.

Значит, проблема не в отсутствии исполнителя, а в отсутствии единого контракта, который однозначно отвечает: какой исполнитель выполнил конкретный запуск, на каком коде, с каким разрешением и где находится окончательный отчёт.

Это центральная доработка. Её нельзя решать ещё одним CI, который автоматически посылает задания на ВМ.

## 4. Целевая архитектура: разделить четыре контура

Я бы не строил одну большую GitHub-автоматизацию, которая пытается управлять всем. Нужны четыре связанных контура с разными полномочиями.

1\. Научная память

R / C / L / U / предпосылки / N / D / источники / решения

Источники истины и научная генеалогия

2\. Управление работой

Issues → Project V2 → branches → PR → Review

Задачи, полномочия, решения о технических изменениях

3\. Исполнение

Фиксированный SHA → run plan → VM / sandbox → отчёт

Воспроизводимость и ресурсная бухгалтерия

4\. Приёмка и сохранение знания

Техническая проверка → научное рассмотрение → D / R / U обновления

Научные статусы не меняются автоматически

GitHub Actions обслуживает воспроизводимые технические операции. Issues и Projects организуют работу. Git хранит версионированное знание и свидетельства. ВМ исполняет вычисления. Агент помогает пройти путь между ними, но не становится научным приёмщиком.

### 4.1. Научная память: добавить D, не копировать реестр в Issues

В предыдущем обсуждении мы выделили Research Decision Record. Я считаю, что его нужно встроить в эту архитектуру.

Предлагаю отдельный тип узла:

`decision:D001`

Его поля:

```
decision_id: D001
status: PROPOSED

question: "Какую архитектуру использовать?"
scope:
  - C042
  - R128
  - U010

alternatives:
  - id: A
    disposition: REJECTED
    rationale: "..."
  - id: B
    disposition: SELECTED
    rationale: "..."
  - id: C
    disposition: DEFERRED
    rationale: "..."

proposal:
  author: assistant

ratification:
  authority: user
  status: PENDING

evidence:
  - R128
  - source:path/to/report.md

consequences:
  constrains: []
  enables: []
  supersedes: []
  reopens: []

revisit_conditions: []
```

Нужно различать `PROPOSED`, `RATIFIED`, `SUPERSEDED`, `REOPENED`. Агент вправе подготовить D-запись, но не переводить её в `RATIFIED` самостоятельно.

Связи D с R/C/L/U/N должны проходить через тот же типизированный граф. Не нужно создавать Issues для всех R-записей или заменять реестр доской Projects.

Предлагаемая структура:

```
decisions/
    D001.yaml
    D002.yaml

continuity/
    ACTIVE_STATE.json
    SESSION_HISTORY.md
```

`ACTIVE_STATE.json` — компактная точка восстановления сессии: текущий базовый SHA, активные задачи, D-записи, работающие и завершённые `run_id`, открытые противоречия и следующий шаг. Это не вторая научная база и не источник онлайн-статуса ВМ.

### 4.2. Управление работой: один Project V2

Конфигурация из PR №3 хорошая. Я бы сохранил её и добавил только несколько полей.

| Поле         | Тип           | Назначение                                                  |
| ------------ | ------------- | ----------------------------------------------------------- |
| Status       | Single select | Inbox / Analysis / Ready / Running / Review / Done / Parked |
| Work kind    | Single select | Science / Analysis / Code / Infrastructure / Documentation  |
| Permission   | Single select | Read-only / Docs / Code / Local compute / VM-authorized     |
| Lineage      | Text          | Родители R/C/L/U/N                                          |
| Decision IDs | Text          | Связанные D-записи                                          |
| Run ID       | Text          | Идентификатор исполнения, если применимо                    |
| Next action  | Text          | Одно следующее действие                                     |
| Acceptance   | Text          | Наблюдаемый критерий завершения                             |
| Budget       | Text          | Предел времени и ресурсов                                   |

Представления доски:

- Inbox — новые задачи.
- Analysis — исследование и проектирование.
- Ready — подготовлены источники, критерии и разрешения.
- Running — реально исполняемые задачи.
- Review — техническая и научная проверка.
- Blocked / Parked — зависимые и отложенные задачи.
- Done — рабочее завершение.

`Done` означает только завершение рабочей карточки. Это не закрытие U и не перевод R в подтверждённый статус.

Я бы включил автоматическое добавление только для Issues и PR с меткой `work:active`, а не для всех изменений и не для научных карточек. Автоматическое добавление в Projects не является задним заполнением: уже существующие элементы потребуется добавить отдельно.&#x20;

Для меток достаточно небольшой системы: `work:active`, `kind:science`, `kind:code`, `kind:infra`, `needs-decision`, `blocked`. Метки не должны использоваться для разрешения запуска ВМ или изменения научного статуса.

Discussions, Wiki и Pages сейчас не включал бы. Wiki будет дублировать документацию в Git, Pages создают дополнительный публичный интерфейс, Discussions пока не нужны для одного основного исследовательского контура. У нас нет проблемы нехватки мест для текста — есть задача обеспечить непрерывность и происхождение решений.

## 5. Исполняемый контур: самое важное техническое изменение

Это главный блок доработки. Он должен обеспечить непрерывную цепочку:

\\[ \text{постановка} \to \text{разрешение} \to \text{исходный SHA} \to \text{исполнение} \to \text{отчёт} \to \text{проверка} \to \text{интеграция}. \\]

### 5.1. Единый контракт запуска

Сейчас `CURRENT_RUN.json` уже содержит хорошую основу: идентификатор задания, SHA исходников, конфигурационный digest, отпечаток среды, прогноз и ресурсные ограничения. Но для будущей автоматизации я бы сделал отдельный неизменяемый `RUN_PLAN.json` на каждое исполнение.

Пример состава:

```
{
  "run_id": "unique-run-id",
  "experiment_id": "X26_OR_X27_OR_NOW",

  "lineage": {
    "results": [],
    "constructs": [],
    "open_questions": [],
    "decisions": []
  },

  "source": {
    "repository": "IgorSabirov/vm-lab",
    "commit": "full-40-character-sha",
    "tree_sha": "...",
    "input_manifest_sha256": "...",
    "config_sha256": "..."
  },

  "executor": {
    "kind": "VM",
    "executor_id": "VM Compute 81"
  },

  "authorization": {
    "authorized_by": "user",
    "authorization_ref": "...",
    "scope": "...",
    "expires_at": "..."
  },

  "budget": {
    "forecast_seconds": 0,
    "hard_wall_seconds": 0,
    "memory_limit_mib": 0,
    "disk_limit_mib": 0
  },

  "acceptance": {
    "expected_workload": {},
    "required_artifacts": [],
    "technical_checks": []
  }
}
```

Числа здесь иллюстративные, а не действующие лимиты. Правило 600 секунд сохраняется без изменений.

Особенно важно: идентификатор задачи и разрешение на её выполнение — разные объекты. В действующем `github_bridge.py` входная заявка имеет только `run_id` и `commit`. Это достаточно для маршрутизации, но не является самостоятельным доказательством полномочия на выполнение произвольного пакета.

Нужно связать план исполнения с конкретным разрешением и ограничить его срок, целевой исполнитель, допустимую команду и бюджет. Автоматическая система не должна считать, что наличие Issue или PR автоматически разрешает вычислительный запуск.

### 5.2. Неизменяемая история исполнения

Я бы дополнил `CURRENT_RUN.json` следующими объектами:

```
runs/<run_id>/
    RUN_PLAN.json
    RUN_EVENTS.ndjson
    PROCESS.json
    RESULT_MANIFEST.json
    TECHNICAL_REVIEW.json
    SCIENTIFIC_REVIEW.json
```

Назначение:

| Файл              | Что хранит                                          |
| ----------------- | --------------------------------------------------- |
| RUN_PLAN          | До запуска: SHA, конфигурация, разрешение, прогноз  |
| RUN_EVENTS        | Хронология переходов очереди и исполнения           |
| PROCESS           | Фактические время, CPU, объём задач и состояние     |
| RESULT_MANIFEST   | Полный перечень выходов, размеры и SHA-256          |
| TECHNICAL_REVIEW  | Проверка целостности и соответствия плану           |
| SCIENTIFIC_REVIEW | Отдельная оценка научного утверждения и ограничений |

Статусы исполнения должны быть явными:

`PREPARED → SUBMITTED → QUEUED → RUNNING → COMPLETED`

и альтернативные исходы:

`FAILED`, `CANCELLED`, `INTERRUPTED`, `UNKNOWN`.

Нужно также отдельно хранить статус технического гейта:

`PASS`, `REVIEW_REQUIRED`, `NOT_EVALUABLE`.

Научный статус — отдельный реестровый объект.

Это позволяет автоматически отвечать на вопросы «какой именно код исполнялся», «что реально выполнено» и «почему отчёт отличается от плана», но не отвечает автоматически на вопрос «подтверждена ли гипотеза».

### 5.3. Изменить публикацию результатов до включения защиты main

Сейчас `github_bridge.py` отправляет результат прямым push в `main`.

Я предлагаю другой путь:

ВМ завершила run

`results/<run_id>/` — отчёт, манифест, метрики, контрольные суммы

Изолированная ветка результатов

`results/<run_id>` — без перезаписи ранее опубликованного запуска

Pull Request

Проверка SHA, полноты экспорта, размера и структуры файлов

Интеграция в main

Результат сохранён; научная приёмка остаётся самостоятельной

Плюсы:

- результат не может незаметно изменить основной реестр;
- конфликт с параллельным изменением `main` становится видимым;
- отчёт проверяется на том же SHA, с которого он получен;
- неудачные и прерванные задания также могут быть опубликованы как технические свидетельства;
- можно запретить запись результата в существующий `run_id`.

Нужно избегать самоссылки в хешах. `RUN_PLAN.json` содержит хеши исходников и конфигурации. `RESULT_MANIFEST.json` содержит хеши файлов результата, но не должен пытаться включить собственный итоговый хеш. Весь результат затем закрепляется отдельным Git commit.

Полный архив данных не нужно переносить в Git при каждом запуске. GitHub должен хранить протокол, краткий отчёт, метаданные и контрольные суммы. Большие массивы остаются на ВМ либо во внешнем хранилище, ссылка и манифест сохраняются в Git. Это согласуется с уже существующим разделением `report/` и `full/` в `github_bridge.py`.

Именно этот пункт нужно реализовать до включения защиты `main`, потому что иначе старый мост будет пытаться писать туда, куда новая политика уже не разрешает.

### 5.4. Не ставить GitHub Actions runner на вычислительную ВМ

Здесь я бы не стал идти по распространённому пути «подключить собственный runner и запускать всё через Actions».

У нас ВМ — отдельный вычислительный исполнитель с собственными данными, очередью, checkpoint и правилами доступа. GitHub предупреждает, что self-hosted runners могут сохранять последствия компрометации после выполнения недоверенного кода или workflow. Поэтому я не рекомендую делать пользовательскую ВМ универсальным Actions runner, особенно для PR из экспериментальных веток.&#x20;

## 6. GitHub Actions: вместо одного универсального workflow — матрица технических проверок

Я не предлагаю 20 workflow. Нужна небольшая система из нескольких независимых проверок.

| Workflow / job      | Что проверяет                                                            | Когда запускается                        |
| ------------------- | ------------------------------------------------------------------------ | ---------------------------------------- |
| `repo-integrity`    | Реестр, D/N, типизированные связи, хеши и генерацию                      | Каждый PR и изменение научных материалов |
| `infra-tests`       | `github_bridge`, result reader, launch control, Copilot bridge, recovery | Изменение `infra/` и `tools/`            |
| `core-tests`        | E002d/E002e и соответствующие регрессии                                  | Изменение соответствующих модулей        |
| `experiment-tests`  | NOW integration, X27 v0.4.3/v0.5.1                                       | Изменение исполняемых пакетов            |
| `workflow-security` | Права workflow, закрепление действий, опасные паттерны                   | Изменение `.github/`                     |
| `run-receipt-check` | Полнота и целостность опубликованного результата                         | Изменение `results/`                     |
| `merge-gate`        | Сводит ожидаемые проверки в один обязательный статус                     | Каждый PR                                |

### 6.1. Почему нужен отдельный merge-gate

GitHub имеет важную особенность: когда workflow целиком пропущен из-за `paths`/`branches`-фильтра, обязательный статус может остаться `Pending` и блокировать слияние. Поэтому я бы не делал единственный обязательный workflow условным через глобальный `paths`.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://docs.github.com\&sz=32)

GitHub Docs+2



Лучше:

- `merge-gate` запускается на каждом PR;
- внутри него вычисляется, какие области реально затронуты;
- соответствующие тестовые jobs выполняются условно;
- финальный gate завершает проверку после обработки всех ожидаемых jobs и выдаёт один стабильный статус.

Тогда PR, меняющий только документацию, не запускает весь X27-пакет. Но PR, меняющий `infra/github_bridge.py`, не может случайно пройти без регрессии моста.

### 6.2. Что именно запускать

Нынешний корневой `tests/` содержит E002 и тесты реестра. В `infra/` лежат отдельные тесты моста, запуска, публикации и восстановления. В `experiments/` лежат NOW и X27 тесты.

Я бы сохранил независимые команды для этих пакетов, а не делал один глобальный `unittest discover` по всему дереву: так в запуск не попадут тесты из `results/VM_WORKSPACE_SNAPSHOTS/` и исторических копий.

У каждого пакета должен быть явный контракт:

- какая версия Python и зависимостей нужна;
- точная команда запуска;
- что считается техническим PASS;
- какие входы и фикстуры требуются;
- какие тесты — быстрые регрессии, а какие — калибровка или научное исполнение.

Особенно важно: Actions не должен запускать длительные научные сетки автоматически при каждом push. Он должен проверять инфраструктуру и небольшие детерминированные контроли. Научный прогон запускается только через отдельный run plan, действующее разрешение и гейт времени.

### 6.3. Безопасность workflow

Что уже сделано хорошо в `Registry links`:

- `permissions: contents: read`;
- checkout закреплён по полному SHA;
- `persist-credentials: false`;
- ограничение времени;
- отмена устаревшего запуска.

Это нужно сохранить и распространить на остальные workflow.

Дополнительно:

1. Каждый job получает только нужные permissions, а не общие права на весь workflow.

2. Actions закрепляются полными SHA. GitHub рекомендует immutable SHA pinning как наиболее надёжный вариант против подмены действия.&#x20;

   [image](https://www.google.com/s2/favicons?domain=https://docs.github.com\&sz=32)

   GitHub Docs+1

3. Добавить статический аудит workflow через `actionlint` и `zizmor`.

4. Обновить checkout до Node 24-совместимого релиза, закрепив полный SHA: сейчас в Actions виден warning о Node 20 deprecation.

5. Dependabot оставить PR-only. Автоматическое слияние обновлений не включать.

6. Добавить проверку секретов и запретить попадание токенов, ключей и приватных конфигураций в артефакты.

Текущий Dependabot в PR №3 обновляет только GitHub Actions раз в неделю — это хорошее начало. Зависимости экспериментальных Python-пакетов нужно обслуживать отдельно, с явными lock/constraint-файлами для каждого исполняемого пакета, а не одной общей версией Python-зависимостей на весь большой репозиторий.

## 7. Агентная автоматизация: что действительно стоит подключить

Здесь GitHub в 2026 году предлагает более интересную возможность, чем Issue Forms: Agentic Workflows. Функция вышла в GA 28 октября 2026 года. Она позволяет описывать агентные workflow в Markdown с YAML front matter, компилировать их в Actions и оставлять агенту чтение и анализ, а отдельному механизму — ограниченные безопасные операции записи.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://github.blog\&sz=32)

GitHub Changelog+2



Но я бы не давал агенту право вести научный реестр самостоятельно.

Предлагаю начать с трёх помощников.

### 7.1. Issue Triage Agent

При появлении Issue:

- читает формулировку;
- предлагает тип задачи;
- ищет кандидатов R/C/L/U/N/D;
- показывает возможных родителей;
- отмечает недостающие данные;
- оставляет комментарий с рекомендацией.

Он не создаёт новую R-запись, не закрывает U и не присваивает научный статус.

### 7.2. CI Failure Analyst

При провале Actions:

- читает логи;
- отделяет ошибку окружения от дефекта кода;
- обнаруживает устаревший сгенерированный индекс;
- предлагает точное место исправления;
- оставляет комментарий с диагностикой.

Не исправляет и не сливает код автоматически. Это особенно полезно, поскольку PR №3 уже показал повторяющиеся ошибки синхронизации производных файлов.

### 7.3. Decision Draft Agent

После завершения содержательного PR:

- готовит проект D-записи;
- извлекает альтернативы, основания и ограничения из PR и комментариев;
- связывает D с R/C/L/U/N;
- указывает, какие последствия ещё не проверены;
- сохраняет запись в состоянии `PROPOSED`.

Никогда не переводит D в `RATIFIED`. Это остаётся за Вами.

Для всех трёх агентных workflow:

- `contents: read`;
- без доступа к секретам;
- без связи с VM Compute;
- без запуска расчётов;
- без автоматического merge;
- безопасный выход — только комментарий к исходному Issue/PR или draft-предложение.

Агентные workflow не заменяют детерминированные Actions. Они должны объяснять неуспех, искать связи и формировать предложения, а не удостоверять истинность.

Есть техническая оговорка: Agentic Workflows компилируются в lock-файлы. Версии `gh-aw` нужно закреплять и проверять; релизы `0.83.3–0.85.3` были отозваны по причине уязвимости, поэтому нельзя брать произвольную старую версию.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://github.com\&sz=32)

github/gh-aw: GitHub Agentic Workflows · GitHub+2



Текущий `infra/copilot_bridge.py` при этом сохраняется: он выполняет роль технического ревью готового кода. Не нужно заменять его агентом GitHub или смешивать техническую проверку Copilot с научной оценкой.

## 8. Публикация версий, архив и защита данных

В репозитории уже 17 140 объектов и примерно 141 MiB по размеру API. Дальше количество результатов и снимков может расти очень быстро.

Я бы ввёл правило:

Git хранит научные тексты, код, протоколы, манифесты и небольшие проверяемые отчёты. Полные тяжёлые вычислительные данные хранятся отдельно, с неизменяемой ссылкой и контрольными суммами.

В частности:

- не копировать полный VM workspace в Git при каждом запуске;
- не дублировать один и тот же архив в нескольких ветках без причины;
- использовать манифест с SHA-256, размером, источником и точкой восстановления;
- в Git сохранять краткий отчёт и указатель на полный массив;
- архивные snapshots хранить как архивы, не как активную часть CI.

GitHub Actions artifacts не подходят в качестве единственного долговременного архива. Для приватных репозиториев стандартный максимальный срок хранения артефактов — 400 дней с 1 октября 2026 года; это ограничение платформы, а не обещание постоянной научной памяти.&#x20;

### Releases и tags

Сейчас Releases нет. Я бы ввёл их, но редко:

- выпуск замороженного экспериментального пакета;
- выпуск воспроизводимой версии протокола;
- выпуск версии инфраструктурного инструмента.

Release должен ссылаться на определённый commit и manifest. Это архивная отметка версии, не научный статус. Не нужен отдельный Release на каждый запуск.

### Что оставить выключенным

Не включать сейчас Wiki, Pages и Discussions. Не создавать публичный сайт с автоматическим экспортом приватных результатов. Не включать общую GitHub App с широкими полномочиями, пока нет конкретной необходимости.

## 9. Порядок внедрения: зависимости и блокирующие решения

Я бы делал не двадцать параллельных PR, а шесть последовательных этапов.

| Этап                                 | Содержание                                                                                     | Зачем                                  |
| ------------------------------------ | ---------------------------------------------------------------------------------------------- | -------------------------------------- |
| 1. Разобрать PR №3                   | Rebase на `71b45a2`, сохранить CCC review, N-долги и все изменения реестра, пересобрать индекс | Не потерять уже выполненную работу     |
| 2. Зафиксировать контракт исполнения | Run plan, разрешение, идентификаторы исполнителя и результата, immutable receipt               | Сделать мост и MCP согласуемыми        |
| 3. Перенести публикацию результатов  | Ветка `results/<run_id>` и PR с манифестом, без прямого push в `main`                          | Подготовить безопасную защиту main     |
| 4. Построить CI-матрицу              | Реестр, инфраструктура, E002, NOW/X27, security, merge-gate                                    | Проверять изменённые компоненты        |
| 5. Включить защиту main и Project V2 | PR-only, обязательный gate, запрет force-push, рабочая доска                                   | Закрепить дисциплину изменений         |
| 6. Подключить агентов и D            | Decision Records, ACTIVE_STATE, issue triage, CI failure analysis, D draft                     | Создать преемственность между сессиями |

### Что является блокером

Блокер №1 — решение по тарифу GitHub. Для приватного репозитория сильная серверная защита требует GitHub Pro или Team. Оставить репозиторий публичным ради бесплатной защиты я не рекомендую.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://docs.github.com\&sz=32)

GitHub Docs+1



Блокер №2 — переход публикации результатов на PR. Пока `github_bridge.py` пушит прямо в `main`, включать обязательный PR-only режим нельзя: мы заблокируем существующий маршрут результата.

Блокер №3 — согласование PR №3 с текущим main. Нельзя просто нажать Merge из-за `dirty` и отсутствующей в PR записи CCC review.

### Что не является блокером

Project V2 можно создать после согласования полей. Issue Form и PR template уже достаточно хороши, их не нужно многократно переписывать. Агентные workflow можно подключить позже, после устойчивого CI и защищённого пути публикации.

## 10. Какой результат я предлагаю считать завершением этой доработки

Не количество файлов и workflow, а следующую проверяемую способность:

Новая исследовательская задача может пройти весь цикл от постановки до сохранённого результата и следующей сессии без потери происхождения, полномочий, ограничений и истории решений.

Проверка должна выглядеть примерно так:

1. Создаётся Issue с одним конкретным вопросом и родителями.
2. Проектируется D-запись, если предстоит содержательный выбор.
3. Подготовленный код закрепляется полным SHA.
4. Run plan содержит разрешение, конфигурацию и бюджет.
5. Расчёт выполняется на согласованном исполнителе.
6. Результат публикуется с манифестом, хешами и точным source commit.
7. CI проверяет техническую целостность.
8. Научный отчёт явно отделяет вычисленное, доказанное, предполагаемое и не установленное.
9. Пользователь принимает решение о научном статусе.
10. Следующая сессия восстанавливает состояние из GitHub, не повторяя уже выполненную работу и не приписывая агенту память, которой у него нет.

## Моя итоговая рекомендация

Я бы сейчас не расширял инфраструктуру новыми шаблонами. Три главных изменения, которые действительно изменят качество нашей совместной работы:

1. `D` — долговременная память принятых решений.
2. `RUN_PLAN → RESULT_MANIFEST → result PR` — единый безопасный исполняемый контур.
3. Матрица CI с обязательным стабильным merge-gate и защищённой `main`.

После них Project V2 станет полезной рабочей панелью, а агентные workflow — содержательными помощниками, а не декоративной автоматизацией.

Существующий PR №3 я бы не выбрасывал и не переписывал. Его следует сохранить как первый инфраструктурный интеграционный пакет, аккуратно синхронизировать с текущим `main` и отделить его уже сделанные части от следующих трёх архитектурных изменений.

Никаких изменений в `vm-lab` я не вносил. Сверка завершена на `71b45a2`; это архитектурная рекомендация, а не уже выполненная миграция.

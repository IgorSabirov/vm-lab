# Что ещё можно использовать в GitHub для интеграции научных репозиториев

Я проверил непосредственно текущую конфигурацию `IgorSabirov/vm-lab`.

Есть существенное изменение: репозиторий уже имеет статус Public. При этом GitHub подтверждает для подключённого доступа права администратора, записи и обслуживания репозитория. Значит, сейчас можно рассматривать не только чтение внешних проектов, но и полноценную архитектуру интеграции с PR, CI и защищёнными точками приёмки.

[Открыть vm-lab](https://github.com/IgorSabirov/vm-lab?utm_source=chatgpt.com)

У Вас уже реализована довольно развитая инфраструктурная основа:

- `development.yml` — выборочные тесты по изменённым областям и общий технический merge gate;
- `failure-advisor.yml` — автоматическая диагностика неудачных проверок;
- `registry-advisor.yml` — помощь при изменениях реестра;
- `result-pull-request.yml` — приём результатов через отдельные PR;
- `freeze-release.yml` — фиксация проверенного снимка;
- Dependabot — еженедельная проверка версий GitHub Actions.

Это не пустая инфраструктура, которую нужно заменять новым интеграционным фреймворком. Её лучше расширить специализированным контуром внешних научных зависимостей.

[Посмотреть существующие workflows](https://github.com/IgorSabirov/vm-lab/tree/main/.github/workflows?utm_source=chatgpt.com) · [Dependabot](https://github.com/IgorSabirov/vm-lab/blob/main/.github/dependabot.yml?utm_source=chatgpt.com) · [Разделение науки и инфраструктуры](https://github.com/IgorSabirov/vm-lab/blob/main/SCIENCE_INFRASTRUCTURE_SEPARATION.md?utm_source=chatgpt.com)

Мой главный вывод: сейчас недостаёт прежде всего управления жизненным циклом внешнего научного источника, а не ещё одного исполнительного механизма.

## 1. Самое важное: автоматическое обнаружение изменений в upstream

Сейчас есть возможность сохранять внешние проекты как источники, но нужна полноценная система наблюдения за их развитием.

GitHub предоставляет три взаимодополняющих механизма.

А. Webhooks и GitHub Apps

Можно подписаться на события:

- новый commit;
- новый release;
- изменение ветки;
- создание pull request;
- публикация новой версии.

GitHub App получает уведомления непосредственно от репозитория. Это позволяет практически сразу обнаруживать изменения.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://docs.github.com\&sz=32)

GitHub Docs+1



Б. `repository_dispatch`

Один репозиторий может инициировать проверку в другом.

Например:

```

IsingCauset
    │
    ├── Published release
    │
    ▼
GitHub App / webhook
    │
    ▼
vm-lab: repository_dispatch
    │
    ▼
UPSTREAM_CHANGE_DETECTED
    │
    ├── Compare commits
    ├── Inspect changed files
    ├── Check license
    ├── Run adapter tests
    │
    ▼
Draft Pull Request
    │
    ▼
Human review

```

В. Периодическое обнаружение

Для проектов, к которым нет доступа для настройки webhook, можно использовать scheduled workflow и API GitHub.

Он будет сравнивать текущий upstream SHA с последним проверенным SHA.

GitHub поддерживает `repository_dispatch` и `schedule` как события запуска Actions.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://docs.github.com\&sz=32)

GitHub Docs



Мой вывод: это одна из наиболее полезных недостающих возможностей. Мы должны отслеживать не просто новые версии, а изменения, способные повлиять на уже принятые научные выводы.

## 2. Reusable Workflows — общие вычислительные протоколы

Сейчас `development.yml` уже использует динамическую матрицу тестов. Но среди пяти активных workflows нет общего переиспользуемого workflow с триггером `workflow_call`.

GitHub позволяет вынести процесс проверки в один workflow и вызывать его из разных репозиториев.

Например:

```

vm-lab
  │
  └── .github/workflows/
        ├── development.yml
        ├── validate-external-source.yml
        ├── reproduce-author-control.yml
        ├── adapter-compatibility.yml
        └── scientific-evidence-check.yml

External projects
  │
  ├── IsingCauset ──────┐
  ├── CDT ──────────────┤
  ├── Serbian C++ ──────┼──> Shared validation
  └── ADD ──────────────┘

```

Важный момент: общий workflow может принимать параметры конкретного источника:

```
with:
  repository: author/project
  source_sha: 0123456789abcdef
  adapter: isingcauset-v1
  test_profile: smoke
```

Каждый запуск должен работать с конкретным SHA, а не с плавающей веткой `main`.

Общие workflow можно вызывать из других публичных репозиториев, закрепляя их полным SHA. Это позволяет стандартизировать проверки, не копируя их реализацию.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://docs.github.com\&sz=32)

GitHub Docs+1



Для `vm-lab` я бы сделал именно так: один общий протокол внешней интеграции, а особенности отдельных научных моделей оставил в адаптерах.

## 3. Artifact Attestations — криптографическое происхождение результатов

Особенно рекомендую

Это одна из наиболее интересных возможностей для научного репозитория.

GitHub умеет создавать криптографически подписанные свидетельства происхождения артефактов — Artifact Attestations.

Они позволяют установить:

- какой репозиторий произвёл артефакт;
- какой commit использовался;
- какой workflow выполнил сборку;
- какой именно файл или набор файлов был получен;
- соответствует ли артефакт заявленному происхождению.

Поддерживается проверка подписей через GitHub CLI. Для публичных репозиториев эта возможность доступна и на текущих планах GitHub Free.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://docs.github.com\&sz=32)

GitHub Docs+3



Для vm-lab это можно использовать следующим образом:

```

SOURCE_COMMIT
      │
      ▼
ADAPTER_COMMIT
      │
      ▼
RUNTIME_IMAGE_DIGEST
      │
      ▼
INPUT_DATA_SHA256
      │
      ▼
EXECUTION
      │
      ▼
OUTPUT_ARCHIVE_SHA256
      │
      ▼
SIGNED ATTESTATION
      │
      ▼
RESULT RECEIPT
      │
      ▼
vm-lab scientific registry

```

Здесь нужно строго различать две вещи:

- Attestation подтверждает происхождение и целостность вычислительного артефакта.
- Она не подтверждает правильность физического закона, математического вывода или интерпретации эксперимента.

Но это существенно усилит воспроизводимость и защиту от незаметной подмены результатов.

## 4. GitHub Packages и Container Registry

Я бы использовал GitHub Container Registry (GHCR) для хранения проверенных вычислительных сред.

Например:

`ghcr.io/igorsabirov/vm-lab-isingcauset`

Внутри контейнера:

- компилятор;
- системные библиотеки;
- Python или C++ runtime;
- зависимости;
- адаптер;
- авторские smoke-тесты;
- скрипт воспроизведения контрольного результата.

Для каждого образа сохраняются:

- исходный commit;
- digest контейнера;
- версии зависимостей;
- лицензия;
- результаты авторского контроля;
- SBOM — Software Bill of Materials.

Преимущество в том, что контейнер идентифицируется не только тегом версии, но и криптографическим digest.

Публичные контейнерные пакеты GHCR могут скачиваться без авторизации.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://docs.github.com\&sz=32)

GitHub Docs



Это особенно полезно для проектов, где авторская среда критична для воспроизведения результата.

При этом контейнер — техническая фиксация среды, а не доказательство эквивалентности двух научных моделей.

## 5. Dependency Graph и Dependency Review

Здесь я обнаружил конкретный пробел.

В текущем `.github/dependabot.yml` настроен только:

```
package-ecosystem: github-actions
```

То есть обновления GitHub Actions отслеживаются еженедельно, но Python-зависимости в активных вычислительных проектах не включены в такую же политику обновлений.

Я предлагаю задействовать три возможности.

Dependency Graph

Строит граф зависимостей проекта, включая зависимости, обнаруженные через manifests и специально отправленные snapshots.

Dependency Submission API

Позволяет отправлять информацию о зависимостях, которые не удаётся обнаружить обычным анализом файлов.

Dependency Review

Показывает изменения зависимостей в pull request и помогает выявлять новые уязвимые пакеты до слияния.

Эти возможности особенно интересны для публичного репозитория.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://docs.github.com\&sz=32)

GitHub Docs+2



Я бы добавил:

- pip Dependabot для активных Python-проектов;
- Dependency Review для PR;
- автоматическое формирование SBOM;
- проверку транзитивных зависимостей;
- сохранение конкретных версий и lock-файлов.

Исторические копии исходников в `results/VM_WORKSPACE_SNAPSHOTS` не следует автоматически превращать в активные зависимости: мониторить нужно действующие проекты.

## 6. Rulesets, CODEOWNERS и защищённые научные изменения

В текущей структуре не обнаружен файл `CODEOWNERS`.

Это недоиспользованная возможность.

Можно определить ответственных за разные области:

| Область              | Требуемая проверка             |
| -------------------- | ------------------------------ |
| `.github/workflows/` | Инфраструктурная               |
| `experiments/`       | Научно-методологическая        |
| `analysis/`          | Аналитическая                  |
| `results/`           | Происхождение данных           |
| `registry/`          | Проверка генеалогии и статусов |

GitHub умеет автоматически запрашивать review ответственных за изменённые файлы.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://docs.github.com\&sz=32)

GitHub Docs+1



Вместе с Rulesets можно установить:

- запрет прямых изменений `main`;
- обязательный PR;
- обязательные успешные проверки;
- запрет удаления защищённых тегов;
- повторную проверку после изменения уже одобренного PR;
- обязательное одобрение владельцем соответствующего кода.

Отдельный момент: фактическую конфигурацию действующих branch rulesets я не смог подтвердить через доступный интерфейс GitHub. Поэтому не утверждаю, что их сейчас нет.

Моя рекомендация: отдельно защитить `main` и шаблоны научных релизных тегов. При этом не включать автоматическое научное принятие результатов через CI.

## 7. GitHub Environments и OIDC

Это уже относится к связке GitHub → ВМ → GitHub.

GitHub Environments позволяют выделять отдельные среды, например:

- `smoke`;
- `calibration`;
- `vm-authorized`;
- `scientific-release`.

Критически важные среды можно защищать подтверждением ответственного и ограничениями на ветки и теги.

Для доступа к внешним облачным вычислительным ресурсам есть OIDC: GitHub Actions получает краткоживущую идентичность вместо использования постоянных ключей в Secrets.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://docs.github.com\&sz=32)

GitHub Docs+1



Для vm-lab это потенциально позволяет организовать:

```
GitHub PR
   │
   ▼
Technical validation
   │
   ▼
VM authorization gate
   │
   ▼
Remote compute
   │
   ▼
Result package
   │
   ▼
GitHub receipt PR
```

Но я бы не переносил пользовательскую ВМ в обычную конфигурацию постоянно работающего self-hosted runner.

GitHub отдельно предупреждает, что self-hosted runners не гарантируют чистую изолированную среду и могут быть скомпрометированы недоверенным кодом публичного PR.&#x20;

## 8. GitHub Projects V2 — единая очередь интеграций

Здесь интересная деталь: в `vm-lab` уже имеется [проект конфигурации GitHub Projects](https://github.com/IgorSabirov/vm-lab/blob/main/infra/GITHUB_PROJECT_SETUP.md?utm_source=chatgpt.com).

- Status;
- Work kind;
- Permission;
- Lineage;
- Next action;
- Acceptance;
- Budget.

Но в документе зафиксировано, что Project V2 ещё не был создан.

Я бы реализовал эту доску как очередь текущих работ, а не новый реестр научных результатов.

Предлагаемая последовательность интеграции

1. Inbox

   Обнаружен внешний проект или новая версия
2. Analysis

   Изучение статьи, кода, лицензии и предпосылок
3. Ready

   Контракт интеграции сформирован
4. Running

   Сборка, авторский контроль и адаптерные проверки
5. Review

   Сравнение результатов и научная проверка
6. Done / Parked

   Принятое решение или отложенная интеграция

Важное ограничение: для GitHub Free доступен один автоматический workflow добавления элементов на проект. Наиболее разумно использовать его для Issues и PR самого `vm-lab`, куда поступают все интеграционные предложения.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://docs.github.com\&sz=32)

GitHub Docs



Ещё одно разграничение: доступный мне GitHub-коннектор сейчас не предоставляет операций создания и управления Projects V2. Это ограничение интерфейса подключения, а не GitHub. Для создания доски понадобится авторизованный UI или GraphQL API.

## 9. GitHub Discussions — внешний научный круг

Ещё одна недооценённая возможность — Discussions.

Я бы разделил входящие обращения на четыре категории:

| Категория            | Назначение                             |
| -------------------- | -------------------------------------- |
| Scientific proposals | Предложения новых научных источников   |
| Methodology          | Обсуждение методов и предпосылок       |
| Reproduction reports | Независимые результаты воспроизведения |
| Research updates     | Объявления о новых версиях             |

Discussions отличаются от Issues: это пространство обсуждения, а не обязательно готовая задача.

Полезная последовательность:

`Discussion → Issue → Integration Contract → PR → Scientific Review`

GitHub поддерживает тематические категории, форматы вопросов и ответов, объявления и перенос обсуждений в Issues.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://docs.github.com\&sz=32)

GitHub Docs+2



Для публичного научного проекта это ещё и способ собирать внешние контрпримеры и замечания.

## 11. Что делать с большими вычислительными артефактами

У проекта уже накоплена значительная история результатов и снимков вычислительных пространств.

Здесь стоит задействовать:

GitHub Actions Artifacts — для промежуточных результатов тестов, логов, временных архивов и диагностик.

GitHub Releases — для закреплённых версий проверенного программного пакета и небольших архивов результатов.

Git LFS — для подходящих больших бинарных файлов, которые действительно требуется хранить в Git-репозитории.

Внешний научный архив — для долговременного хранения больших наборов экспериментальных данных с DOI и контрольными суммами.

Одна существенная оговорка: у Actions Artifacts в публичном репозитории максимальный срок хранения составляет 90 дней. Поэтому нельзя превращать их в единственное хранилище научного свидетельства.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://docs.github.com\&sz=32)

GitHub Docs+1



Особенно важно сохранить Ваш принцип:

`RAW DATA → HASHES → MANIFEST → ANALYSIS → RESULT`

а не подменять исходные данные одним красивым итоговым отчётом.

## 12. Ещё одна возможность: CodeQL и OpenSSF Scorecard

Это дополнительный уровень безопасности внешнего кода.

CodeQL позволяет анализировать исходники и обнаруживать классы программных уязвимостей. Для публичных репозиториев GitHub предоставляет Code Scanning без отдельной покупки Code Security.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://docs.github.com\&sz=32)

GitHub Docs



OpenSSF Scorecard помогает оценивать безопасность цепочки разработки: использование зависимостей, настройки CI, защиту ветвей и другие характеристики.

Для нашего исследования это имеет практический смысл:

- обнаруживать небезопасные операции в стороннем коде;
- выявлять подозрительные зависимости;
- проверять workflow внешних проектов;
- обнаруживать небезопасные практики сборки.

Но эти проверки должны оставаться техническими. Они ничего не говорят о правильности физических предпосылок или математической теории.

### Как дополнить существующий научный договор

Ваши шесть пунктов уже задают хорошую основу. Я бы добавил к ним технические атрибуты в существующий `SOURCE_INDEX` и связанные контракты, не создавая ещё одного реестра.

# 15. Очерёдность внедрения

Я бы не стал одновременно включать все возможности.

Мой выбор: сначала P0

| Очерёдность | Работа                     | Ожидаемый эффект                          |
| ----------- | -------------------------- | ----------------------------------------- |
| 1           | Upstream Monitor           | Перестаём пропускать изменения источников |
| 2           | Reusable Validation        | Единый стандарт интеграции                |
| 3           | Provenance и Attestations  | Проверяемое происхождение результатов     |
| 4           | Python dependencies + SBOM | Контроль вычислительных зависимостей      |
| 5           | CODEOWNERS и Rulesets      | Защита научной приёмки                    |
| 6           | Projects V2                | Управление очередью работ                 |
| 7           | Discussions и Citation     | Внешнее сотрудничество и атрибуция        |

Особенно важно: я бы не разрешал автоматическое слияние обновлений внешних научных источников. Даже если тесты проходят, новый commit может менять предпосылки и область применимости результата.

Смена upstream SHA должна запускать ревизию, а не автоматически менять научный статус.

Итоговая рекомендация: сохранить Вашу архитектуру `vm-lab`, добавить к ней автоматическое отслеживание upstream, общий протокол воспроизведения и криптографическую фиксацию происхождения вычислительных свидетельств. Это три наиболее существенных расширения.

Следующий полезный автоматический слой — регулярное обнаружение новых версий внешних проектов с подготовкой отчёта о diff и затронутых научных зависимостях, без автоматического слияния.

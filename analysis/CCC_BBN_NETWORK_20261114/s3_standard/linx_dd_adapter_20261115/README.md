# LINX: адаптер двух D+D-таблиц

Статус: `IMPLEMENTED / ENGINEERING_PASS / FULL_BBN_IDENTITY_PENDING`.
`scientific_acceptance=false`, BBN-интеграций: **0**, GP-реализаций: **0**.

Это реализация согласованного этапа A: передача двух таблиц скоростей в LINX
на существующих узлах. Совместный GP, A/B-перенос ковариации и проверка покрытия
ещё не выполнялись. Успешная проверка RHS не является результатом интегрирования
BBN, оценкой неопределённости D/H или физическим мостом Anthropic–BBN.

## Контракт

`dd_adapter.prepare_dd_tables` принимает ровно `ddHe3n` и `ddtp`, каждый с
полями `t9`, `values`, `encoding`, `units`. Узлы должны точно совпадать с
`Reaction.T9_vec`; обязательны float64 и единицы LINX `cm^3 s^-1 g^-1`.
Преобразование физических GP-скоростей в эти единицы — обязанность будущего
rate-integral модуля, а не скрытая операция адаптера.

1. Копируется исходный вектор `nuclear_rates_q`; только два D+D-элемента заменяются нулями.
2. `precompute_rate_tables(effective_q)` строит все штатные таблицы.
3. Два элемента заменяются внешними значениями; остальные сохраняются побитово.
4. `solve_with_dd` передаёт полный tuple в `AbundanceModel` через локально
   добавленный `rate_tables_override`. Этот низкоуровневый вход не накладывает q повторно.
5. Прямая и обратная реакции используют одну таблицу и штатный detailed balance.

При `linear` передаются положительные скорости; при `log` — натуральные
логарифмы численных значений в указанных единицах. Нулевой или отрицательный
логарифм допустим. NaN/Inf, float32, неверные узлы/формы/порядок и несовместимые
единицы отвергаются на стороне Python до численного вызова.

`solve_with_dd` — проверяемый host-вход для монотонного стандартного охлаждения.
Он намеренно не вызывается внутри JIT/vmap. Для будущего пакетного инференса
каждая реализация сначала проходит host-валидацию, затем передаются только
массивы неизменных структуры, формы и dtype. Проверка повторного использования
JIT сейчас относится к реальному ядерному RHS, а не ко всему BBN-решателю.

## Границы температур

У закреплённых D+D-таблиц диапазон `T9 = 0.001…10`; стандартное начало LINX —
`T9=100`. Поэтому политика по умолчанию `reject` отклонит полный стандартный
интервал. Для линейной интерполяции доступна явно выбранная
`upstream-zero-linear`: вне таблицы сохраняется штатный ноль LINX.
Это сохранение поведения исходного кода, не физическое обоснование GP-хвостов.

В режиме `log` выход из сетки запрещён: исходное `exp(0)=1` вне узлов не
принимается как обоснованное продолжение. По одному этому факту нельзя делать
вывод об ошибке ранее опубликованных прогнозов. Чтобы использовать полный
температурный интервал с log-интерполяцией, требуется отдельное согласованное
решение о хвостах; адаптер сам не расширяет сетку и не меняет физический закон.

Порогов не меняли, научных прогонов не повторяли.

## Воспроизведение

Python 3.12.14, CPU, один доступный CPU через affinity, float64. Из этого каталога:

```sh
python3.12 -m venv .venv
.venv/bin/python -m pip install -r requirements.lock
.venv/bin/python bootstrap.py
.venv/bin/python verify_upstream.py
mv results results_published
.venv/bin/python bounded_engineering.py
```

Bootstrap отказывается перезаписывать `upstream`; supervisor отказывается
перезаписывать результаты. Пакеты и файлы закреплены по версиям/хешам;
результаты хранят хеши исходников, использованных ДО тестов.
В этой среде исходники загружены через GitHub-коннектор и проверены по тем же
хешам; сетевой маршрут `bootstrap.py` отдельно не запускался.

## Следующий критерий приёмки

В разрешённом вычислительном пакете сравнить native-вызов и тождественный
override по конечному вектору абундансов, затем проверить динамическую замену
таблиц на уровне BBN. Обязательны одинаковые q (D+D=0), один и тот же фон,
начальные условия, solver, допуски, узлы и dtype. Нужны отдельные заранее
зафиксированные критерии и фактическая калибровка полного маршрута; инженерное
время выше их не заменяет.

Этап B (совместный GP) независим от A. Сначала A+B→C, затем A/B с неизменными
маргиналами, затем калибровка покрытия. Перед затратной частью каждого этапа
применяется временной gate. `neutt` и физический мост BH1 здесь не требуются.

Этот PR — подготовка, не вычислительный преемник PR #54. `CONTROL`, `CURRENT`,
`RUN_REQUEST`, бюджет и webhook не менялись. На момент проверки очередь
остаётся `BUDGET_WAIT` до 2026-11-15 14:09:29 UTC; само наступление времени
не означает запуск. R/C/L/U и научная приёмка не меняются.

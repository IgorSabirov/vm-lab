## 2. Что содержательно добавляет NOW v0.2

Изменение существенно глубже, чем добавление генеалогических полей.

### 2.1. Единое состояние

Вместо нескольких независимых моделей вводится полное состояние \\(z\\) с шестью согласованными представлениями:

| Обозначение | Содержание                      |
| ----------- | ------------------------------- |
| \\(G(z)\\)  | Носитель и геометрия отношений  |
| \\(Q(z)\\)  | Совместное физическое состояние |
| \\(M(z)\\)  | Память и физические следы       |
| \\(A(z)\\)  | Аппаратура                      |
| \\(R(z)\\)  | Ресурсы, среда и отходы         |
| \\(C(z)\\)  | Сообщения, часы, контроллеры    |

Это важное уточнение: не шесть независимых физических запасов, а шесть представлений одного состояния.

Переход записан как

\\[ z'\sim K_u(\cdot\mid z). \\]

Причём авторы не заявляют, что общий физический \\(K\\) уже получен. Существуют отдельные \\(K\_{\rm NOW}\\), \\(K\_{\rm U008}\\), \\(K\_{\rm X26}\\), но их совместное физическое исполнение пока не построено.

Для оценки организации предлагается профиль продолжения:

\\[ \Pi(z)= \left\\{ \operatorname{Law}(O\_{0:H}\mid z,do(u)): u\in U \right\\}. \\]

Это лучше сравнения отдельных выходных величин: учитываются распределения историй, неуспехи, расходы и сроки.

### 2.2. Генеалогия аппаратов и информации

Введён типизированный граф:

\\[ \Gamma\_{\rm hist}= (\text{версии объектов},\text{события}). \\]

В нём необходимо отдельно регистрировать:

- происхождение аппарата;
- текущего владельца;
- производственное событие;
- передачу;
- использование;
- списание.

Особенно важная оговорка: история исследователя не является бесплатной памятью физического контроллера.

Если два состояния \\(z\\) действительно совпадают полностью, а закон \\(K\\) один и тот же, разные внешние описания прошлого не должны сами по себе изменять дальнейшую динамику. Историческое различие должно иметь физический носитель в настоящем состоянии.

Это устраняет опасную возможность приписывать системе дополнительную причинность посредством внешнего журнала наблюдений.

### 2.3. Три уровня продолжения

| Вариант | Что проверяется                                                      |
| ------- | -------------------------------------------------------------------- |
| H1      | D выполняет функцию с заранее предоставленным аппаратом              |
| H2      | C производит аппарат, передаёт его D, D действительно использует его |
| H3      | D самостоятельно производит средства следующему носителю E           |

H1 и H2 не объявлены ресурсно эквивалентными. H2 не доказывает H3.

Это принципиально важно: наследование готового оборудования не является доказательством наследования производственной способности.

## 3. Самая важная часть: проверка генеалогии по исходному коду

Я отдельно проверил не только новый текст, но и исходники, на основании которых составлялся генеалогический отзыв.

Здесь обнаружены реальные технические ограничения U010.

### 3.1. U008 не проверяет полноценное локальное чтение получателем

В `u008_run.py` при доставке записывается:

```
child.memories = {'received': copy.deepcopy(body)}
```

Но в функции получателя вычисление результата происходит через:

```
a,b = self.child_payload['bits']self.child_output = a ^ b
```

То есть функция использует объект доставленного сообщения, а не результат физического чтения локально записанной памяти.

При этом код проверяет наличие аппаратов чтения и записи и списывает ресурсы. Но проверка наличия аппарата не равна доказательству его причинного участия в получении ответа.

Это очень важное различие.

Поэтому U008 остаётся полноценным результатом в своём объявленном классе, но не доказывает полноценную цепь:

\\[ \text{доставка}\rightarrow \text{запись}\rightarrow \text{чтение}\rightarrow \text{декодирование}\rightarrow \text{использование}. \\]

Обновлённая модель правильно требует эту цепь проверить.

[Исходник U008](https://github.com/IgorSabirov/vm-lab/blob/b919e64ad89a5afe2c395a0218895c856088c57d/experiments/now_integrated_v1/u008/u008_run.py?utm_source=chatgpt.com)

### 3.2. В штатном Engine другой контракт памяти

В `engine.py` предусмотрена последовательность:

1. Получатель принимает биты через `receive_record`.
2. Они попадают в `pending`.
3. `maybe_write` физически записывает их в `memories`.
4. `read` извлекает содержимое посредством механизма чтения.
5. Полученное значение становится частью `decoded`.

Это уже значительно ближе к требуемой физической цепи.

Но U008 использует другую архитектуру сообщения. Следовательно, нужен адаптер между двумя форматами либо отдельная реализация U010.

Нельзя просто передать поле `received` и объявить, что D получил полноценную локальную память Engine.

[Engine](https://github.com/IgorSabirov/vm-lab/blob/da72a3a89176b77ceca75779923029534fd26b99/experiments/now_integrated_v1/nowexp/engine.py?utm_source=chatgpt.com)

### 3.3. Аппаратная передача: два аппарата вместо четырёх

В `local_instruments.py` при отдельной производстве writer/reader создаются четыре аппарата:

\\[ W_0,R_0,W_1,R_1. \\]

Однако стандартный `transfer` в Engine при `separate_apparatus` использует:

```
count = 2
```

То есть переносит последнюю пару, а не все четыре аппарата.

Это не обязательно ошибка. Для H2 пары writer/reader может хватить. Но размер передаваемого комплекта должен быть закреплён в протоколе, а не меняться в зависимости от неявной конфигурации.

### 3.4. Списание аппаратов — наиболее опасная техническая граница

В `local_instruments.py` обнаружено правило:

```
old = [    a for a in cell.apparatus    if a["generation"] < cell.generation    or a.get("production_round", -1)       < cell.production_round - 1]
```

Здесь две проблемы.

Первая. Аппарат C имеет поколение C. При передаче D его поколение не должно превращаться в поколение D. Но при поколениях C=1 и D=2 первая часть условия может списать именно переданный аппарат C.

Вторая. `production_round` — локальный счётчик носителя. Сравнивать напрямую счётчик C с локальным счётчиком D некорректно без дополнительной координаты производителя.

Есть и дополнительный риск: если D успевает выполнить собственное производство перед `retire`, у его исходного порта, не имеющего `production_round`, может сработать вторая часть условия. В штатном `boot` производство назначено перед списанием.

Критический блокер реализации H2

Это пока не доказанный провал эксперимента U010: сам эксперимент не исполнен. Но статический аудит исходников подтверждает, что проблему нельзя игнорировать при проектировании протокола.

Решение должно сохранять идентичность, производителя и историю аппарата, а правило списания должно быть отдельно определено и проверено.

[Правила производства и списания](https://github.com/IgorSabirov/vm-lab/blob/da72a3a89176b77ceca75779923029534fd26b99/experiments/now_integrated_v1/nowexp/local_instruments.py?utm_source=chatgpt.com)

Шесть вопросов, которые действительно блокируют переход к исполнению U010:

1. Формат памяти и адаптер между U008 и Engine.
2. Исполнитель транспорта C→D.
3. Передача пары или четырёх аппаратов.

Отдельно необходимо заранее определить \\(V\_{\rm ready}\\), а не выбирать его после получения результата. Иначе условие

\\[ C(V)\subseteq V \\]

рискует стать тавтологическим: система будет объявлена жизнеспособной относительно области, которую подобрали под её фактическое поведение.

Следующим этапом имеет смысл провести предрегистрационный аудит U010: зафиксировать H1/H2, аппаратуру, ресурсные балансы, порядок событий и проверку списания, прежде чем писать исполнительный код.

## 3. Математическая модель v0.2

[Текст модели](https://github.com/IgorSabirov/vm-lab/blob/main/analysis/COMMON_MODEL_20261109/MODEL.md?utm_source=chatgpt.com) · [Машинная версия](https://github.com/IgorSabirov/vm-lab/blob/main/analysis/COMMON_MODEL_20261109/MODEL.json?utm_source=chatgpt.com)

Я считаю это наиболее важной частью обновления.

Вместо набора независимых моделей предлагается описывать одно полное состояние \\(z\\) посредством согласованных представлений:

\\[ z\longrightarrow (G,Q,M,A,R,C), \\]

где учитываются геометрия и носители, совместное физическое состояние, память, аппаратура, ресурсы, коммуникации и контроллеры.

Переход задаётся общим формализмом:

\\[ z'\sim K_u(\cdot\mid z). \\]

Организация характеризуется не одним скалярным результатом, а профилем продолжения:

\\[ \Pi(z)= \left\\{ \operatorname{Law} (O\_{0:H}\mid z,\operatorname{do}(u)) : u\in U \right\\}. \\]

Это важное методологическое улучшение: в профиль включаются не только правильные ответы, но и неуспехи, ресурсы и сроки.

Для замыкания вводится область допустимых состояний \\(V\\):

\\[ C(V)\subseteq V. \\]

Здесь \\(C\\) — полный цикл: действие, физический след, использование следа, восстановление или производство условий и следующая способность.

Но модель сама подчёркивает собственную границу: \\(K\_{\mathrm{NOW}}\\), \\(K\_{\mathrm{U008}}\\) и \\(K\_{\mathrm{X26}}\\) пока не получены как согласованные ограничения одного физического K.

То есть v0.2 — математическая архитектура синтеза, а не уже построенная единая физическая теория.

## 4. Генеалогия: наиболее ценный технический результат

[Генеалогический отзыв](https://github.com/IgorSabirov/vm-lab/blob/main/analysis/COMMON_MODEL_20261109/NEIGHBOR_GENEALOGY_REVIEW_20261110.txt?utm_source=chatgpt.com)

В модель введён типизированный двудольный граф:

\\[ \Gamma\_{\mathrm{hist}}= (V\_{\mathrm{objects}},V\_{\mathrm{events}},E). \\]

Различаются носители, аппараты, записи, ресурсные партии, каналы и события.

Для каждого аппарата нужно знать:

- неизменяемую идентичность;
- создателя;
- поколение создателя;
- производственный раунд;
- событие рождения;
- родителей и израсходованные ресурсы;
- текущего владельца;
- состояние и историю списания.

Это позволяет устранить важное смешение: аппарат, созданный P и переданный C, не становится аппаратом C. Его происхождение остаётся прежним, хотя владелец меняется.

Отдельно зафиксирован принцип:

Журнал исследователя не является бесплатной памятью контроллера.

Полный граф может быть доступен внешнему наблюдателю, но контроллер способен использовать только физически доступные ему следы. Запись и чтение должны иметь собственную реализацию и стоимость.

Это правильное ограничение для всей программы: генеалогия объясняет происхождение способности, но не превращается в дополнительный управляющий механизм, который тайно знает прошлое.

## 5. Проверка генеалогического отзыва по исходному коду

Я отдельно сверил наиболее важные утверждения с исходниками, закреплёнными на SHA `da72a3a89176b77ceca75779923029534fd26b99`.

### 5.1. Память D пока не обеспечена одним фактом доставки

В `engine.py` получение записи и физическая запись в память — разные операции.

`receive_record()` помещает бит в локальный `pending`, а `maybe_write()` выполняет платную запись в `memories`.

[Исходник: receive_record / maybe_write](https://github.com/IgorSabirov/vm-lab/blob/da72a3a89176b77ceca75779923029534fd26b99/experiments/now_integrated_v1/nowexp/engine.py?utm_source=chatgpt.com#L170-L230)

Следовательно, переданное содержимое ещё не становится памятью D автоматически.

Нужен отдельный адаптер формата U008 к локальным записям Engine либо иной явно реализованный физический путь. Прямая загрузка `decoded` из внешнего журнала не удовлетворяет поставленному критерию.

### 5.2. Передача четырёх аппаратов сейчас не следует из стандартного Engine

В `Engine.transfer` при `separate_apparatus=True` задаётся:

\\[ count=2. \\]

Затем передаются последние два аппарата:

```
moved = cell.apparatus[-count:]
```

[Исходник: Engine.transfer](https://github.com/IgorSabirov/vm-lab/blob/da72a3a89176b77ceca75779923029534fd26b99/experiments/now_integrated_v1/nowexp/engine.py?utm_source=chatgpt.com#L465-L487)

При последовательности `W,R,W,R` D получает последнюю пару W/R, а не все четыре аппарата C.

Это не косметическая деталь: H2 должен заранее определить, проверяется ли перенос функциональной пары или всех произведённых аппаратов.

Правильно, что в v0.2 этот выбор оставлен открытым, а не подменён предположением об автоматической передаче четырёх.

### 5.3. Правило retire может уничтожить только что полученную аппаратуру

В `local_instruments.py`:

```
old = [a for a in cell.apparatus if       a["generation"] < cell.generation       or a.get("production_round", -1) < cell.production_round-1]
```

[Исходник: retire_inherited](https://github.com/IgorSabirov/vm-lab/blob/da72a3a89176b77ceca75779923029534fd26b99/experiments/now_integrated_v1/nowexp/local_instruments.py?utm_source=chatgpt.com#L60-L75)

Здесь две проблемы.

Первая — поколение аппарата C может оказаться ниже поколения D. Тогда аппарат, только что переданный C, при retire может быть классифицирован как унаследованный и списан.

Вторая — `production_round` является локальным счётчиком носителя. Сравнение производственного раунда одного носителя с локальным раундом другого без дополнительной семантики некорректно.

Предложенное представление

\\[ \rho(a)=(\operatorname{creator}(a),\operatorname{creator\\\_round}(a)) \\]

правильно фиксирует, что производственные раунды имеют разные области отсчёта.

### 5.4. Автоматический boot D создаёт дополнительные обязательства

При поступлении `offspring_arrive` Engine вызывает `boot()`. В свою очередь, boot автоматически назначает чтение, производство, retire, ремонт, коррекцию, передачу и запрос снабжения.

[Исходник: boot и offspring_arrive](https://github.com/IgorSabirov/vm-lab/blob/da72a3a89176b77ceca75779923029534fd26b99/experiments/now_integrated_v1/nowexp/engine.py?utm_source=chatgpt.com#L222-L240)

Это означает, что U010 должен определить полный горизонт и управлять автоматическими событиями. Иначе в эксперимент попадут незаявленные производство, списание и ресурсные операции.

Вывод по коду: генеалогический отзыв обнаружил не формальные мелочи, а реальные препятствия для корректной реализации H2.

## 6. Семантический контроль — существенное улучшение протокола

Одна из лучших поправок v0.2 касается проверки содержательного использования записи.

Ошибочная постановка могла требовать, чтобы изменение бита приводило к отказу функции:

\\[ Y\_{\mathrm{function},D}=0. \\]

Но если D прочитал изменённую запись и правильно выполнил функцию над новым содержанием, это не отказ. Это свидетельство причинной роли содержания.

Для XOR:

\\[ f(A,B)=A\oplus B. \\]

При изменении одного входа:

\\[ (A,B)\rightarrow(1-A,B) \\]

правильный результат должен измениться:

\\[ f(1-A,B)\neq f(A,B). \\]

При этом обе ветви должны оставаться функционально успешными относительно собственного входа:

\\[ o_D(m)=f(m), \\]

\\[ o_D(Tm)=f(Tm). \\]

Контроль целостности с корректно пересчитанной checksum отделяется от отдельного контроля повреждения checksum.

Это устраняет методологическую ошибку, при которой причинное использование содержания путали с отказом функции.

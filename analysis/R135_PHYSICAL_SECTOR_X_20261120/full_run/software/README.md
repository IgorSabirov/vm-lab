Проверен код основной ветви на [987667fb](https://github.com/IgorSabirov/vm-lab/tree/987667fb5d5f054c4881af4bf091c45c4755f98f) и фактический исполнитель BBN на [d503ee0f](https://github.com/IgorSabirov/vm-lab/tree/d503ee0f1f89c99c8560803dc46277d544ef15ba/reproductions/BBN_COSMO_20261120/runtime). У этапа две независимые отметки готовности. Первая говорит, умеет ли программа решать задачу и проверен ли её численный результат. Вторая фиксирует происхождение и достаточность физических входов. ## Исполняемый пакет P0–P10

Поставлены общий исполнитель `r135-stage`, исполнитель явного графа зависимостей
и численные модули всех стадий. Их исходники находятся в [r135](r135), проверки —
в [tests](tests). P0 переиспользуется без изменения замороженных физических фактов:
48 диагностических, 4 литературных и 0 независимо калиброванных точек X.

### Установка и команды

Работать из checkout репозитория; код использует закреплённые соседние источники.
Базовые зависимости: Python 3.11+, NumPy и SciPy. Необязательные родные решатели
имеют отдельные закреплённые среды, описанные в backend/BACKENDS.md.

```sh
d=analysis/R135_PHYSICAL_SECTOR_X_20261120/full_run/software
python -m pip install -r "$d/requirements-core.lock"
python -m pip install --no-deps -e "$d"
python -m unittest discover -s "$d/tests" -v
python -m unittest discover -s "$d" -p 'test_p0_register.py' -v
r135-stage --help
```

В checkout без установки тот же CLI доступен как `python "$d/r135_stage.py"`.
`--seal` связывает явно заданные конфигурацию и входы с SHA кода и содержимым файлов:

```sh
r135-stage --seal --stage P0 --config "$d/examples/p0.json" \
  --template "$d/examples/request.validation.json" --out /tmp/r135-p0-request.json
r135-stage --stage P0 --request /tmp/r135-p0-request.json --out /tmp/r135-p0-result
r135-stage --verify /tmp/r135-p0-result
```

Пример сопряжённого P7 — `examples/coupled_control.json`: полностью заданный
диагностический закон, пять историй и проверяемые балансы. Для него используются
`--seal --stage P7 --template examples/request.coupled.validation.json` и конфигурация
`examples/coupled_control.json` из каталога пакета, затем обычный вызов P7. Его параметры не
объявляются физической калибровкой X.

Для P1–P10 действует та же команда. JSON-запрос содержит стадию, ключ
`claim_id/model_id/point_id/thermal_path`, режим, область применимости,
конфигурацию и хешированные входные артефакты. Режим `validation` предназначен
для явно диагностических проверок; `conditional` сохраняет условность внешних
модельных подготовок; `physical` требует независимо подготовленную точку P0.
Для двух последних режимов байты исполняемых модулей должны совпадать с указанным
коммитом. Неполный вход даёт `OPEN_INPUT`, повреждённый или несовместимый — отказ.
Научную приёмку ни один режим не назначает.

`r135-stage --pipeline plan.json --out result/` исполняет явный граф запросов:
родитель указывается через `from_node` и точное имя артефакта. Исполнитель проверяет
родительский манифест и хеш, сохраняет запрос каждого шага, продолжает независимые
ветви и не пересчитывает уже проверенный результат того же запроса. Итоговые файлы
фиксируются атомарно, частичные файлы при исключении сохраняются для диагностики.
Для одной и той же папки запрещено незаметно менять входы или подмешивать новые файлы.

[Проверки и точные результаты](VALIDATION.md) относятся к программной реализации.
Полный физический R135 этим изменением не запускается; трекер #155 остаётся открытым.

## Контракт исполнителей

Единица запуска — стадия, модель, физическая точка и тепловая ветвь; для ансамблей добавляются идентификаторы решётки, цепи и участка цепи. Подготовка регистрирует независимые параметры до открытия отложенных исходов. Имя входа P1–P10 определяется полями requires и requires_for_claim в PLAN. До запуска фиксируются SHA кода, данных и конфигурации, единицы, параметры, точности, исполнитель и доступный ресурс. Каждая запись результата содержит ключ, происхождение, единицы, ошибку и статус. Абсолютное физическое время, шаг графа и шаг Марковской цепи получают разные имена.

Общий вызов P1–P10 реализован: `r135-stage --stage Pn --request request.json --out result/`. Значение Pn заменяется на P1, P2, …, P10. Обязательные атрибуты запроса — execution SHA, хеш конфигурации, модель/точка/ветвь, режим, входные артефакты с хешами и допустимый диапазон. Старый контракт infra/run_contract.py допускает только зафиксированный Python-entrypoint без аргументов. Для исполнения через него следует упаковать запрос в проверенный файл и вызывать фиксированную обёртку без аргументов. Если расширять сам общий контракт, сохранить совместимость со старыми квитанциями.

Статусы решения, исключения, открытого входа и технической ошибки задаёт PLAN. Обработчик прекращает зависимое вычисление, когда вход отсутствует или находится вне области применимости, пишет точную причину и оставляет независимо исполнимые ветви в очереди. Для повторов фиксируются PRNG и состояние решателя, временный каталог и атомарная фиксация только после проверки файлов. Процесс аудита отдельно проверяет путь каждого результата до источника и читает сохранения без права менять исходные данные.

## Исполнимый вход P0

Команды из корня репозитория, Python 3.11 или новее, стандартная библиотека:

```bash
d=analysis/R135_PHYSICAL_SECTOR_X_20261120/full_run/software
out=$(mktemp -d)/p0
python "$d/p0_register.py" freeze --out "$out"
python "$d/p0_register.py" verify --out "$out"
python -m unittest discover -s "$d" -p 'test_p0_register.py'
```

Снимок воспроизводится из [исходных записей](register_inputs.json) и текста PLAN. Чтобы заморозить другую редакцию, передать `--registry путь/к/записям.json` и новый выходной каталог. На тех же входах повтор идемпотентен. Существующий снимок с другим содержимым проверка отклоняет. [Реестр моделей и точек](p0_snapshot/model_register.json) · [зафиксированные наблюдательные данные](p0_snapshot/data_release_lock.json) · [правила и открытые прогнозы](p0_snapshot/decision_rules.json) · [SHA-256](p0_snapshot/P0_SHA256.json).

В снимке две архитектуры, три научных утверждения, 48 диагностических точек и четыре внешние модельные подготовки X-B. Число космологических точек с независимо установленным абсолютным масштабом X остаётся равным **0**. Для четырёх внешних подготовок получены размерные координаты на холодной стороне перехода и диапазоны чувствительности. Файлы P0 содержат ссылки на измерения и исходные условия. [Исходные подготовки, расчёт и границы вывода](xb_reference/README.md).

В наблюдательном реестре закреплены D/H по Cooke, доля гелия по Aver и три компонента Planck PR3. Архив ESA, все используемые файлы, матрицы, nuisance-параметры, совместный SZ-приор и среда исполнения имеют воспроизводимую привязку. Контроль ΛCDM вычислен на полном TT,TE,EE+lowE. [Пакет Planck и команда повтора](planck_pr3/README.md) · [Cooke et al.](https://arxiv.org/abs/1710.11129v3) · [Aver et al.](https://doi.org/10.1088/1475-7516/2015/07/011).

## Порядок поставки кода

1. Забрать закреплённый P0 и зафиксировать оставшиеся физические подготовки/релизы. Параллельно разрабатывать P1 и независимую обработку/генерацию P3, строить P2 для графовой линии. Для независимой космологии SU(3) графовое отображение не стоит на критическом пути.
2. Разрабатывать P5 и P6 как вызываемые библиотеки с единым соглашением о состоянии и размерностях. P4 нужен для тезиса о причине запаздывания. При доказательно закрытом механизме отсечь только зависящие от него утверждения.
3. P7 интегрирует P5 и P6 на одной истории. **Первое межмодульное испытание передачи энергии** — при ненулевом консервативном источнике температура у стенки меняет фазовую скорость, а изменение доли фазы возвращается в источник. Сверить раздельные балансы и размер ошибки обратной связи на уточнённой сетке.
4. P8, P9 и P10 можно разрабатывать на сохранённых независимых историях и артефактах PR #144 до появления полного P7. Для научной сдачи используется именно физический выход соответствующего родителя P7. Аудитор проверяет цепочку входов отдельно от совпадения конечного числа.

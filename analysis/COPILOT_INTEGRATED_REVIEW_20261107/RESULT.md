## Разбор замечаний авторами проекта

Разбор ниже выполнен по исходникам, без запуска модели. Метка «принято» означает
принятую техническую проблему, не внесённое исправление и не выполненный тест.

| Замечание | Решение | Основание / следующий конкретный шаг |
|---|---|---|
| Commit — только строка, не проверенная связь с файлами; при resume можно сменить эту строку | ПРИНЯТО | Digest вычисляется, но связь с GitHub commit не удостоверяется, commit не входит в fingerprint. Нужен манифест файлов, закреплённый за commit; сверка содержимого и commit при resume. На изолированной ВМ допустим архив без `.git`, поэтому одной проверки `git HEAD` недостаточно. |
| Причинные родители инструментов сведены к boot | ПРИНЯТО | Состояние контроллера локально, но `parents` не содержит полную причинную цепь доставки, записи, чтения, расхода и коррекции. Добавить события фактических переходов и ссылки на использованные локальные записи/ресурсы. |
| `hard_wall_seconds` проверяется дискретно; потерянное после checkpoint время не учитывается при resume | ПРИНЯТО | Это пока кооперативный предел, способный превыситься внутри шага. Согласовать внешний контроль времени и журнал затрат всех попыток; учитывать время неуспешного сегмента, не смешивая его с временем целой траектории. |
| При неопределённом интервале контракт всё равно получает positive/negative return по точке | ПРИНЯТО | `statistical_interpretation=UNRESOLVED` записывается отдельно, но `realized_return` уже выбран по среднему. Отделить описательное совпадение от научного решения; при неразрешённой статистике возвращать `unresolved_return`. |
| Часть обещаний предкам оценивается неподходящим одним скаляром | ПРИНЯТО | R064 требует число поддержанных поколений; R074 — одинаковый родитель и различающийся потомок; R120 — совместный профиль, стоимость и средства; R121 — разделение содержания/аппарата; R123 — действительное опоздание доставки. Число выбирается, но результат от него не зависит. Увеличивать эти клетки до 512 повторов не требуется. Полезная отдельная защита — автоматически проверять право конфигурации на метку deterministic. |

Один результат может обслуживать несколько конкретных обещаний. Объявлять их независимыми подтверждениями нельзя; это уже ограничено в протоколе и должно остаться явным в отчёте. |
| Все роли нового A не проверяются на том же носителе после retire | ПРИНЯТО КАК ГРАНИЦА ОБЕЩАНИЯ | Чтение и производство идут до retire; после retire новый A ремонтирует/корректирует/передаётся, а чтение и производство проходит у потомка. Если обещана проверка каждой роли после замены на том же носителе, нужен соответствующий вызов/контроль. |
| После успешного resume может остаться FAILED.json | ПРИНЯТО | Нужен однозначный финальный статус с историей неудачных попыток. Удаление истории затрат не является исправлением. |
| Полный log в каждом checkpoint и повторные обходы каталога могут быть дороги | ПРИНЯТО КАК КАНДИДАТ ОПТИМИЗАЦИИ | По коду видно накопление/копирование log и сканирование файлов; фактическая цена ещё не измерена. Не объявлять ускорение без эквивалентности снимка и измерения после ревизии. |
| Разные указания registry commit в первоначальном ТЗ и коде | УТОЧНЕНИЕ ПРОИСХОЖДЕНИЯ | Постановка ссылалась на `55a9e69…`; код собран поверх `0cf0f11…` и опубликован в `18aa961…`. Это последовательные срезы, не два взаимоисключающих результата. Их роли надо явно записать в SOURCE, а не менять старую историю. |

Дополнительные полезные замечания: хранить фактически использованные входные
биты и времена доставок в строках всех траекторий; сравнивать общий отклик
и различие профилей в одном evaluation; не путать заданный нулевой эффект
повторной идентичной записи с новым физическим законом; сохранённые сырые
профили ещё не означают, что обещанный анализ этих профилей выполнен.

## Что ревизия дала генеалогии

Она обнаружила именно опасность, указанную пользователем: обещания уже записаны,
но ряд автоматических verdict проверяет более узкий скаляр. Если оставить это
как есть, отчёт формально вернётся ко всем предкам, не выполнив часть обещаний.
До запуска требуется исправить сопоставление «обещание → наблюдаемая → критерий».
Старые прогнозы сохраняются в commit 18aa961; изменение метрики и её порогов
должно быть явной предзапусковой ревизией, не послепрогонной подгонкой.

Это технический результат ревизии постановки. Он не подтверждает I_C/I_H/I_G,
не добавляет физический результат R126 и не закрывает L01–L10.

## Уточнения к мнению соседей

Главный диагноз и запрет ослаблять assert приняты. Контрасты сами по себе не создают задач. Формула объёма должна учитывать finite_enumeration, фазовый выбор режимов, дополнительные MC и design controls. Проверка forecast.task_count находится в runner.context, а не непосредственно в provenance.gate.
0.754 с — время unittest, не прогноз ВМ. Отсутствие запуска ВМ не доказывает отсутствие расходов работающей машины или расхода ассистента. Ноль расходов не заявляем.
Предыдущий unittest был запущен без --failfast: после обнаружения FAIL он закончил свой набор. Затем дальнейшие стадии остановлены. Формулировка «при первом FAIL мгновенно остановлено исполнение тестов» была бы неточной. Для следующего диагностического запуска использовать --failfast.
Часть snapshot/restore уже проверялась unit-тестами; полный supervisor/recovery smoke не пройден. PASS 17 новых тестов не доказывает полную самосогласованность новых ветвей.

## Алгоритм работы именно для этого ремонта

1. Закрепить исходный SHA, команду, среду и полный лог STOP; не исправлять историю результата.
2. Получить разбор; записать принятые замечания, уточнения и границы ремонта.
3. Исправить источник рассогласования и всех его писателей/читателей. Сохранить охранный assert; добавить отрицательный контроль дрейфа.
4. Проверить состав без траекторий, сохранить новую версию протокола и исходный коммит. Повторно выпустить source receipt для этого SHA; старые квитанции не редактировать в PASS.
5. Выполнить unit с --failfast, затем полный bounded runner/recovery smoke. При любом STOP сохранить следующую точку разбора и прекратить последующие стадии.
6. После PASS — актуальная калибровка на целевой ВМ, новый прогноз по фактическим фазам и I/O; сравнить с неизменёнными hard limits до submit.
7. Freeze и main по действующему поручению/протоколу. Научные статусы повышать только по соответствующим результатам.

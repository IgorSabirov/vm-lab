## Что действительно проверено

Первый процесс получил случайный код и ответил `SAVED`. Он завершился.
Второй, новый процесс открыл ту же сессию по явному UUID и получил только
вопрос о прежнем коде. Код повторно не передавался. Ответ точно совпал:
`BRIDGE_MEMORY_fe6702184387`. Оба кода завершения — 0.

Применены `--session-id`, `--output-format json`, `--stream on`, локальные
`--share` и `--usage-output-file`. В первой пробе получено 16 событий,
во второй — 23. Во время второй пробы, при статусе RUNNING, уже читались
шесть событий, включая начало запроса модели; окончательного ответа ещё
не было. После завершения созданы Markdown-переписка и файл расхода.
Синхронизация с облачной историей была отключена; gist не создавался.

Проверена память между **нормально завершившимися процессами на той же
машине**. Не проверены аварийное завершение посреди ответа, потеря машины,
диска или авторизации, долгий разговор и исчерпание лимита.
Один успешный опыт не измеряет частоту отказов.

Автовыбор модели изменился между вопросами: первый обслуживала
`mai-code-1.1-flash`, второй — `gpt-6-luna`. Сохранённая беседа продолжилась,
но постоянный номер диалога не означает постоянную модель. Для сравнения
решений следует записывать фактически выбранную модель; при необходимости
воспроизводимого сравнения — явно выбирать доступную модель.

Доказательства: [evidence.json](evidence.json), вопросы и статусы в
`round_1/`, `round_2/`. Опубликован сокращённый журнал событий: тип, время,
текст отправленного вопроса/окончательного ответа, выбранная модель,
результат. Внутренняя диагностика провайдера и промежуточные рассуждения
не входят в этот журнал. Полный профиль CLI и авторизационные данные не
читались и не сохранялись в репозиторий.

## Полезные возможности и границы

| Возможность | Польза для нас | Уровень подтверждения |
|---|---|---|
| Явный UUID сессии | Возвращаемся к нужному разговору без повторной пересылки всей истории | Две живые пробы выше |
| Поток JSONL | Видим поступившие события до полного ответа; можем сохранить частичный результат | Проверено выше |
| Экспорт переписки и расхода | Есть материал для сверки и контроля бюджета | Создание файлов проверено |
| SDK: сохранение/возобновление сессии | Управление из программы, подписка на события | Официальная документация; SDK здесь не запускался |
| Удалённый просмотр CLI | Возможность наблюдать разговор из GitHub/телефона | Документация; не включено |
| Облачная задача | Исполнение на стороне GitHub, отдельно от текущей машины | Документация; доступ аккаунта и живой запуск не проверены |

В текущем основном `infra/copilot_bridge.py` эти новые возможности ещё
не включены. Этот опыт — проверка основы будущего расширения, не готовая
служба фоновой работы.

## Что необходимо добавить к мосту

Это инженерное предложение по результатам проверки, а не описание уже
развёрнутой системы.

1. **Паспорт разговора:** UUID на исследовательскую задачу, закреплённый
   SHA кода, цель, ограничения, решения пользователя. Явно возобновлять
   нужный UUID; не выбирать просто «последний разговор». Краткую карточку
   решений хранить отдельно от длинной переписки, чтобы её сокращение
   моделью не уничтожало договорённости.
2. **Журнал доставки:** до отправки сохранять уникальный `request_id`,
   вопрос и его хеш. Затем фиксировать наблюдаемые этапы: подготовлено,
   процесс запущен, получены события, ответ сохранён, процесс завершён.
   Событие начала и выданный номер сообщения не доказывают завершение.
   Сохранять результат сразу, а не только в памяти ассистента.
3. **Восстановление без дублей:** при разрыве сначала читать тот же журнал
   и проверять прежний процесс. Если исход неизвестен, ставить UNKNOWN,
   а не повторять вопрос вслепую. Продолжение сессии само по себе не даёт
   гарантии однократного исполнения. На одну сессию — один активный
   отправитель, очередь остальных вопросов. SDK прямо предупреждает,
   что встроенной блокировки конкурентного доступа нет.
4. **Понятный статус:** время отправки, последнее событие, готовность
   ответа, конкретная ошибка. Живой процесс и обновление служебного
   статуса не доказывают продвижение модели. Превышение прогноза вызывает
   проверку и сообщение, не самовольное убийство процесса.
5. **Независимое исполнение:** для работы при закрытом чате нужен
   отдельный постоянно работающий исполнитель с устойчивым диском и
   доступом к сервису, либо облачный агент GitHub. Перенос только номера
   сессии не переносит локальную историю и не сохраняет запущенный процесс.
   Подготовленное ТЗ и итоговый ответ сохранять в приватном GitHub;
   секреты авторизации туда не переносить.

Порядок: сначала расширить текущий мост журналом и явной сессией; затем
проверить восстановление после контролируемого сбоя; после этого переносить
исполнение на постоянную машину или проверенный облачный канал. Текущий
порядок ожидания без обрыва со стороны ассистента остаётся в силе.

## Что уточнила документация

- Удалённый просмотр CLI — доступ к процессу на исходной машине. Она
  должна оставаться включённой и в сети. Синхронизация истории даёт
  просмотр; она сама по себе не включает удалённое управление.
- У облачного агента есть отдельный API заданий: создание, список,
  получение состояния. Это позволяет строить связь без пересылки
  сообщений человеком и без обязательного посредничества issue.
  API в public preview, требует подходящего пользовательского токена;
  токен установки GitHub App не подходит. Облачный агент доступен на
  платных планах; наш проверенный CLI-вход не подтверждает такой доступ.
- В SDK cloud sessions документирована конкретная гонка: если отправить
  первый вопрос до `session.start` от `copilot-agent`, вопрос может быть
  отброшен, хотя метод вернёт `messageId`. Нужно подписаться на события
  заранее, дождаться готовности и только затем отправлять. Это особенно
  важно для будущего облачного моста.
- Ограничения из присланного обзора нельзя переносить на все варианты:
  59 минут — предел сессий на GitHub Actions. Ограничение изменений одним
  репозиторием также относится к Actions; новые cloud sandbox sessions
  могут работать с несколькими репозиториями. Эти сведения не задают
  тайм-аут нашему CLI.
- Документация описывает обновлённый облачный интерфейс с 28 октября
  2026. Поэтому доступность и ограничения нужно проверять по выбранной
  среде, а не по старому общему описанию «Copilot».

Регламент исследования не меняется: Copilot предлагает; ассистент
проверяет и обсуждает; неразрешённый содержательный спор решает пользователь.
После его решения спор закрывается и решение реализуется.

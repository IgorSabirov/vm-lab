# E002c — исполняемая реализация v001

Код: ветка `experiment/e002c-v001`. Точка входа: корневой `run.py`;
настройки: соседний `config.json`. Численная модель: `e002c_exp/`.
Протокол: `E002c.md`. Проверки реализации: `E002c_VALIDATION.md`.

## Порядок работы

1. Ассистент закрепляет исходный коммит и уникальный run_id.
2. По команде запуска ассистент отправляет через VM Compute заявку
   `data/vm_lab_queue/<run_id>.json` с полями `run_id` и `commit`.
3. Существующая служба ВМ получает именно этот коммит и запускает `run.py`.
4. Программа пишет `report/` и `full/`; служба сама публикует report в GitHub.
5. Ассистент проверяет закреплённый GitHub-отчёт: сначала время и объём,
   затем хеши, массивы и научные показатели. Пользователь принимает работу.

Эта публикация кода **не отправляет заявку**. Службы, ключи, очередь и старые
результаты не изменяются. Отчёты не переносятся ассистентом с ВМ вручную.

## Два отдельных режима

Корневой config сейчас задаёт **calibration**, run_id `E002c_CAL_v002_r001`:
12 случаев: 8×T20, 2×T5, 2×T40 при dt=.01 = 25000 шагов / 100000 интеграционных RHS.
Предварительный прогноз ВМ: 240 с, диапазон 60–720 с. Включены настоящие
диагностики, матричные снимки, экспорт и проверка экспортированных массивов.
`VM_SOURCE_COMMIT` и `VM_SOURCE_DIR` выставляет существующий GitHub bridge.
Имя исходной папки ВМ должно совпасть с config.run_id.

**production** включает IC-поиск, его проверку, обязательную серию QS/RR
и условный IC transfer. Для него нужен отдельный коммит config с новым run_id,
принятой калибровкой и измеренной формулой времени. Обязательные поля:

```json
{
  "mode": "production",
  "run_id": "UNIQUE_PRODUCTION_RUN_ID",
  "calibration": {
    "report_commit": "FULL_40_CHARACTER_REPORT_SHA",
    "source_commit": "FULL_40_CHARACTER_CALIBRATION_SOURCE_SHA",
    "kernel_sha256": "FROM_CALIBRATION_METRICS_ENVIRONMENT",
    "scipy_version": "FROM_CALIBRATION",
    "numpy_version": "FROM_CALIBRATION",
    "accepted_by_user": true
  },
  "forecast": {
    "seconds_per_step": 0,
    "fixed_seconds": 0,
    "relative_band": 0.4,
    "source": "PINNED_CALIBRATION_AND_EXPLICIT_FORMULA"
  }
}
```

Это схема обязательных полей, не готовая конфигурация: нулевая стоимость шага
отклоняется. Измеренный полный цикл уже включает диагностику и I/O; второй
раз их прибавлять нельзя. Формула фиксируется до очереди и применяется
к заранее определённым объёмам реально выбранной условной ветки.
Основной режим блокируется без калибровки, при изменении ядра/целевых данных,
версий NumPy/SciPy или при недостатке свободного диска. Прогноз не меняется
задним числом. Число потоков BLAS — 1, задаётся до импорта NumPy.

Точный новый состав и основание прогноза: `calibration_v002.json`. Он заменяет
калибровочный раздел исторического plan.json; основной состав сохранён.
Локальная проверка пути calibration имеет runtime-статус NOT_EVALUABLE для
прогноза ВМ: её фактическое время сохраняется, но машины не отождествляются.

## Файлы программы

- `e002_exp/model.py`: неизменённый операторный код E002b из
  `556736fd5c6b23c22b24751accab63932a7c4825`.
- `e002c_exp/provenance.json`: SHA256 исходной модели, целей и подготовленного плана.
- `model.py`: фазовый hop, детюнинг, QS/RR/IC, восемь масок, K/D и балансы.
- `diagnostics.py`: редукции, частичные транспозиции, шесть GME-шаблонов и сертификаты.
- `engine.py`: RK4, сетки .2/2, физичность, стационарность и парное продолжение.
- `fitting.py`: три Powell-старта, жёсткий лимит 16 вызовов на старт, только шесть структурных целей.
- `ic_status.py`: чистая таблица структурного/транспортного статусов IC.
- `comparability.py`: один класс стационарного сравнения и отдельный общий интервал [190,200].
- `analysis.py`: зазоры, маршруты, фазовые разности, взаимодействия и отдельные научные статусы.
- `export.py`: NPZ, сертификаты, полные экстремумы, самодостаточный RESULT и контроль объёма.
- `verify.py`: независимое чтение только экспортированного пакета; engine и full/ не используются.
- `task.py`: оркестрация и предварительные проверки.

Исходный `plan.json` и его генератор сохранены без изменений как закреплённая
спецификация. Их исторические поля readiness описывают подготовку 29 октября;
текущая готовность реализации указана в `E002c_VALIDATION.md`.

## Проверки

Из корня ветки:

```sh
OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 python -m unittest discover -s tests -p 'test_*.py' -v
OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 python -m unittest discover -s infra -p test_e002c.py -v
OPENBLAS_NUM_THREADS=1 PYTHONPATH=. python infra/check_e002c_export_budget.py
```

Проверка кеша, полученного **из одного коммита GitHub**, после выполнения ВМ:

```sh
OPENBLAS_NUM_THREADS=1 python infra/verify_e002c_report.py \
  --github-cache /path/to/downloaded/run-directory \
  --report-commit FULL_REPORT_SHA --source-commit FULL_CODE_SHA --run-id RUN_ID
```

В кеше лежат `run.json`, `output.log`, `files/`. Первая строка проверки —
фактическое полное время из run.json, прогноз и статус; далее проверяются
опубликованные файлы и численные таблицы. Внутренний таймер задачи не включает
последнюю сборку отчёта; это явно отражено в checks.json и не заменяет run.json.

## Явные определения реализации

- Средние последнего окна: интеграл Симпсона по чётным моментам последних
  10 единиц (шесть точек), присутствующим в несжатых числах экспорта.
  Полные сетки .2/2 сохранены на ВМ. Это позволяет независимо пересчитать средние.
- `tau90` требует хотя бы 10 единиц окончательного пребывания в полосе;
  иначе null с причиной. Без стационарности также null.
- NaN допускается только в NPZ для недопустимых условных диагностик;
  поле valid и schema задают причину. В JSON используется null.
- Состояния не нормируются и не исправляются после шага RK4. Симметризация
  используется только для устойчивого вычисления собственных значений после
  отдельной проверки эрмитовости; эволюционирующая rho не заменяется.
- Парные численные ошибки вычисляются на полных общих сетках, а приёмщик
  независимо проверяет их на опубликованном подмножестве. Максимумы на пропущенных
  отсчётах и full-state проверки остаются заявленными результатами кода на ВМ.
- Снимки и progress записываются; автоматического перезапуска прерванной задачи
  из checkpoint в v001 нет. После прерывания нужен отдельный разбор и новый run_id.
- Ни один исход не запускает damage. Семейство свидетелей не полно; отсутствие
  сертификата GME не является доказательством сепарабельности. Фано не подтверждается
  одним провалом тока; автоматический положительный вердикт Фано не выдаётся.

Полная локальная проверка (быстрые тесты, интеграционные тесты со smoke,
калибровочный путь на локальной машине, максимальный экспорт):
`python infra/validate_e002c_prelaunch.py`. Скрипт не отправляет заявок на ВМ.

Принятые и отклонённые замечания: `E002c_PRELAUNCH_REVIEW.md`.

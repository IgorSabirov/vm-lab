# Повтор первого представителя после диагностики BLAS

ENV v002: прогноз0,25с [0,15;1,5], полный процесс0,250547с (+0,22%).
Отчёт GitHub c510291cff5f85231be1cc4e1973d0997bb4698d проверен полностью.
Пустой threadpoolctl объясняется системными последовательными BLAS/LAPACK
3.12.0 (/usr/lib/x86_64-linux-gnu/blas и lapack), а не OpenBLAS-пулом.
Зафиксированы SHA256 всех шести загруженных библиотек и один поток процесса.

E002e_SOLVER_CAL_v001_r002 повторяет ровно заявленный состав r001 с прежними
точностью, моделью, потолком8ГиБ и неоткалиброванным ориентиром120с [10;900].
Теперь для unmanaged BLAS обязательно точное совпадение паспортов библиотек
с ENV v002 и один поток перед запуском. Число вычислительных потоков наблюдается
каждые50мс во время каждой фазы (один служебный поток наблюдения исключается),
при обнаружении дополнительного потока этап отвергается. Сохраняются CPU и
wall time фаз. Микроскопические изменения между отсчётами не исключены.

Это уточнение проверки реально установленной библиотеки, не отключение
контроля потоков. Первоначальный FAILED сохраняется. Состав задач не расширен.
Новые научные данные F2 не вычисляются.

Для последующей baseline-проверки закреплены точные опубликованные QS/RR
узловые блоки и примитивы при T200, dt=.005. На окне190–200 максимум дрейфа
блоков QS8,69e-12; RR1,05e-7, rhs RR2,84e-8. Для проверки эквивалентности
стационарного решателя конечной траектории используются пределы10^-8 (QS)
и5×10^-6 (RR) на примитивы/узловые блоки; это отдельный допуск конечного
горизонта и не ослабляет согласие LU/GMRES. Для IC опубликованного E002d
аналога нет, потому baseline-эквивалентность IC не выдумывается.

# Главный результат — один переносимый файл

[Директива 11 ноября: наука отдельно от инфраструктуры](SCIENCE_INFRASTRUCTURE_SEPARATION.md).

## Генеалогия и экономия работы — прямое правило 6 ноября 2026

Каждый новый эксперимент и содержательный аналитический шаг заранее связывать
с C/R-родителями и, где применимо, L-пробелом единого реестра. До собственного
анализа/кода проверить сохранённые ответы и литературу; применимое готовое
решение использовать, вычислять только оставшийся вопрос. Зафиксировать
ожидаемое изменение родителей, критерии исходов, полный бюджет и остановку.
Итог возвращать в ту же генеалогию с таблицей «было → план → получено → стало»,
выполнением главного вопроса и планом/фактом затрат. Новизна и количество
записей не являются KPI. Учебные опоры, применение литературы, собственные
выводы, вычисления и технические проверки различать.

Обязательный порядок и короткие поля существующего протокола/итога:
[RESEARCH_LINEAGE.md](RESEARCH_LINEAGE.md). Применять без повторного запроса
на уже разрешённую работу; не назначать из этого массовый аудит старых ветвей.


## Зачем

`run.json` — служебный манифест, не самостоятельный научный отчёт. Перечень файлов
не передаёт их содержимое. Ссылка на приватный репозиторий не гарантирует доступ
другому ИИ. Для обсуждения пользователь должен иметь возможность передать один
небольшой обычный текстовый файл без доступа получателя к GitHub и без распаковки.

## RESULT.md для следующих прогонов

Первый содержательный блок — научный вопрос и ответ: что установлено, при каких
предпосылках и с какой неопределённостью. Достоверность доказательства/расчёта
и ограничения данных указать отдельно от технического исполнения.

Обязательная проверка времени помещается в технический блок: прогноз, диапазон,
факт, отклонение, статус и разбор. Недостаток сведений обозначается там
NOT_EVALUABLE; технический статус сам по себе не блокирует научное обсуждение.
Если проблема затрагивает основания вывода, назвать конкретную зависимость и
ограничить этот вывод, сохранив независимые результаты.
Порядок исполнения: [RUNTIME_GATE.md](RUNTIME_GATE.md).

До запуска определяется состав `report/RESULT.md`. Целевой размер — до 24 КиБ UTF-8.
Превышение требует пересмотра представления с сохранением обязательной информации;
тихое обрезание, удаление провалов или выбор только удачных случаев запрещены.

Обязательное содержимое:

- run_id, исходный коммит, версия протокола; что именно проверяли;
- минимальные определения модели, параметров, величин и единиц;
- заранее заявленные ожидания и фактический ответ;
- все условия/группы, конечные главные показатели и сравнение с ожиданиями;
- проверки с фактическими значениями, допусками и всеми провалами;
- план/факт объёма работы, время и результат его разбора при отклонении;
- динамика главных величин и их экстремумы по всем сохранённым отсчётам,
  с временами экстремумов, разбросом и числом исходных записей;
- ограничения вывода и описание не включённых подробностей;
- размеры данных, источники и ссылки/хеши для углублённой проверки.

Длинные повторяющиеся манифесты и полные ряды не дублируются. Статистики считаются
до отбора временных точек, чтобы короткие пики не исчезли из главного результата.
Округление явно указывается; первичные данные не округляются ради экономии.
Для большого числа условий допустим компактный полный ранжир с крайними
случаями и отдельной явной таблицей всех провалов. Потери детализации описываются.

## Два уровня чтения

1. Обычное обсуждение: передать один `RESULT.md` целиком, а не ссылку на run.json.
2. Строгая техническая приёмка и новые вопросы: исходный проверяемый отчёт GitHub.

Компактный файл не заменяет проверку хешей всего исходного экспорта и не доказывает
свою подлинность сам по себе. Проверенные файлы можно повторно читать из кэша
одного закреплённого коммита, проверяя их хеши, без повторного скачивания.

Подробные CSV/JSON следующих прогонов можно публиковать в gzip без потери чисел,
если это заранее внесено в состав отчёта, отражено в манифесте и проверяется
приёмщиком. Читаемый RESULT.md сохраняется отдельно. Не перепаковывать задним
числом исходный проверенный набор и не менять действующую службу ради этого документа.

## Первый пример и границы внедрения

[Самодостаточный итог CONT](infra/reviews/E001X_CONT_GH_v001_r001/RESULT.md) —
ретроспективное представление уже опубликованного и проверенного отчёта.
Исходные run.json, checks.json, metrics.json, таблицы и манифест не менялись.
Размер оригинального набора в GitHub остаётся 9 099 728 байт; экономится
обычная пересылка и повторное чтение главных результатов, не историческое хранение.

Генератор примера: `infra/build_cont_result.py`. Он использует только копии файлов,
полученных из закреплённого коммита GitHub; перед созданием текста заново проверяет
весь набор через github_result_reader.py. Сырые файлы с ВМ ему не нужны.
Генератор специально ограничен этим CONT, чтобы не выдавать неподходящие выводы
для другого эксперимента. Для следующих задач RESULT.md должен формироваться
самим кодом задачи и публиковаться ВМ вместе с остальным отчётом.

Воспроизведение примера (cache содержит run.json, output.log и files/):

```sh
python3 infra/build_cont_result.py --github-cache /path/to/github-cache \
  --report-commit fc7726bc30f21513200eb300fb76b6eba2c4e853 \
  --source-commit f0c182527a9d1fd9208a56cbb1894d82510e4c79 \
  --output infra/reviews/E001X_CONT_GH_v001_r001/RESULT.md
```

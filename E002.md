## Вопрос и ограничения

PP после повреждения восстанавливает hop-перенос лучше независимого обновления
RR при согласованных населённостях рёбер и диссипативных потерях?
Измерять фактическую подпитку, signed ledger и долю form/idle. Даже положительный
ответ не доказывает автопоэзис, универсальную необходимость обратной связи,
когерентности, BIC или отсутствие классической реализации.

Менять базовую точку post-hoc по карте или по J0 нельзя.
Модель 216: три узла 2 уровня, три ребра 0/R/L. Параметры g=.5, J=1,
eta=.25, delta=.1, kappa_in=kappa_out=.5, phi_n=phi_e=.05,
gamma_r=.05, gamma_bg=.01. J0 меняет только J. Время в единицах Jref=1.
Начало RRR × равная смесь |100>,|010>. Все источники и помпа включены постоянно.
`no_feed` здесь означает отсутствие возврата уничтоженного L в R, НЕ отключение eta.

## Повреждения

Локально на каждом из трёх рёбер, без постселекции/нормировки:
- none: I;
- link: Kkeep=P0+PR, Kjump=|0><L|;
- feed: Kkeep=P0+PR, Kjump=|R><L|;
- resource: Kkeep=P0+PL, Kjump=|0><R|;
- hard: Ka=|0><a|, a=0,R,L.
Последовательное применение по трём рёбрам равно произведению локальных CPTP-карт.
Сумма K†K=I. Узловые маргиналы мгновенно не изменяются. Матрица 200− сохраняется
отдельно; строка t200 в основном ряду означает 200+, интегралы recovery не
пересекают разрыв. Предповрежденческое окно хранится отдельно.

## RR: устранение произвольного масштаба времени

Убираем H_form и условный idle; сохраняем H_hop, pump/break/background,
узловые source/sink и дефазировки. Добавляем sqrt(alpha_e) B+ и sqrt(beta_e) B−,
тождественные на узлах и остальных рёбрах. RR остаётся квантовой моделью hop,
не является CTMC-двойником всей системы.

Источником чисел служит уже проверенный неповреждённый `j1_PP_fine` T200
из J0, коммит отчёта d4a20d665dca2e263917269699b53254620c12b5.
Данные — data/e002_rr_target.json. Они закреплены в config, не выбираются
по damage-результатам. Новый PP pre-window и RR проверяют matching заново.

Для каждого ребра l=<PL>, r=<PR>, d=<L_idle†L_idle> из PP:
    beta = d/l
    alpha = (delta+gamma_bg+beta) l/r
Тем самым совпадают населённость и диссипативная потеря активных связей
k l, k=delta+gamma_bg+beta. В стационаре она равна NET когерентному току
образования PP. Это НЕ частота прямых/обратных когерентных «скачков»:
у гамильтоновой конверсии нет такого однозначного классического счётчика.
Не называем контроль полностью matched по микроскопическому обороту.

Почему не least-squares: стационарно p0=delta/eta*pL на каждом ребре,
pR=1−p0−pL. Суммарные inventory/pump/break зависимы от трёх pL.
Один matching населённостей оставляет произвольные времена обновления.
Дополнительные три loss-условия задают шесть alpha/beta однозначно.
Нет оптимизатора, лимита 200 дорогих evaluations или подбора по F/hop.

RR2: alpha2=2alpha, beta2=2(beta+delta+gamma_bg)−delta−gamma_bg.
Это сохраняет целевые населённости и удваивает суммарные потери; просто удвоить
alpha/beta при фиксированных break/background означало бы менять и населённости.
RR2 — проверка чувствительности, НЕ гарантированные границы всех bias.

Matching на новом fine pre-window: три pL, inventory, pump, break и три loss
с PP, максимум относительной ошибки ≤10% (знаменатель max(|target|,1e−12)).
Для RR2 loss-цель удвоенная. F/hop не подгоняются; расхождения публикуются.
При непрохождении — RR_matched_poorly, сильного primary-вывода нет.

## Метрики и допуски

Baseline каждого варианта — fine none среднее [190,200]. Проверяется полное
состояние на окне10: ||Lrho||/||rho||≤1e−6, Δrho/||rho||≤1e−5,
ΔF≤1e−10+1e−4|Fкон|. Нестационарный baseline не даёт сильного сравнения.

Lambda_hop = integral[200,300] max(0,1−Ihop/Ihop_ref)dt.
Hop определён при Ihop_ref>max(1e−8,.05 Ihop_ref_PP).
Lambda_total аналогично, F_ref>max(1e−8,.01 F_ref_PP).
У J0 Lambda_hop=None, а не ноль. У RR_J0 также неопределена Lambda_total.

QF=Qhop+Qform+Qidle+stored, stored=n2(200+)−n2(300).
Доли определены только при QF>max(1e−8,.01 QF_none_same_variant_same_window).
Абсолютный численный пол нужен при нулевом baseline. Все интегралы знаковые;
клиппинг применяется ТОЛЬКО к дефициту Lambda. Не маскируем накопление/слив.
Residual sink и inventory ≤1e−4+1e−5|QF| — квадратурный допуск, не RK4.
Machine guard для КАЖДОГО варианта: Mmachine_damage≤Mmachine_none_fine+.20.
None используется на том же окне; стационарные .26 не подставляются.
При неопределённой доле guard=None; положительный исход запрещён.

Полное dt/2: все none/link, feed PP/QQ/RR. |ΔLambda|≤max(.05,.01|Lambda_fine|),
|ΔM|≤.01, max Δ наблюдаемых≤2e−5. resource/hard без полного уточнения,
не служат основанием сильного вывода. Все численные провалы остаются в checks.

## Классификация заранее

Для primary PP_link против RR_link:
1. Неполнота/численный провал/нестационарный baseline/неопределённая метрика → metric_undefined.
2. Matching RR не прошёл → RR_matched_poorly.
3. Lambda_hop_PP>50 → no_repair_within_window (операциональный порог дефицита).
4. Lambda_hop_RR≤1e−8 → control_deficit_too_small, не деление на ноль.
5. Lambda_hop_PP>0.7 Lambda_hop_RR → repair_not_better_than_control.
6. Guard None → metric_undefined; guard False → machine_heavy_recovery.
7. Иначе network_repair_controlled.

Тот же расчёт с RR2 публикуется рядом, основной контроль не меняется после результата.
Смена исхода при RR2 ограничивает вывод устойчивостью к выбранной скорости.
«Не лучше на 30%» не равно «контроль не хуже»: это отсутствие заранее требуемого преимущества.
Machine-heavy — флаг состава потока, не доказательство причины самого восстановления hop.

Квалификаторы по образованию PP/QP, PQ/QQ, PS/QS; по idle PP/PQ, PP/PS:
отношение Lambda≤.8, обе метрики валидны и guard левого варианта пройден.
Частичные/отрицательные сравнения сохраняются. Это кандидаты гейтового механизма,
не «класс C» квантовой необходимости. CTMC/strong-dephasing в этот запуск не входят.
RR меняет не только обратную связь, но и прямые form/idle каналы; даже успех
не идентифицирует единственную причину. Доли, стоимость и baseline-различия обязательны.

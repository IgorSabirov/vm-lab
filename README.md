| GitHub `results/<run_id>/` | `run.json`, журнал и `files/` с подробным отчётом среднего объёма |
| Чат | Моё объяснение проверенного отчёта и твоё решение |

## Один запуск

1. Я пишу код и параметры в GitHub. Ожидаемый ответ теста указан до запуска.
2. Фиксирую полный SHA коммита и номер запуска. ВМ получает именно эту версию.
3. Передаю на ВМ через VM Compute `write_work_file` заявку
   `data/vm_lab_queue/<run_id>.json` с полями `run_id` и `commit`.
4. По этой заявке ВМ получает код из GitHub, выполняет его, оставляет полные данные у себя.
5. Служба сама записывает отчёт и файлы в GitHub. Расчёт не нуждается в открытом чате.
6. Я читаю `run.json` и указанные в нём файлы через GitHub, закрепив коммит отчёта.
   Проверяю исходную версию, номер запуска, код завершения, размеры и SHA256 файлов.
7. Рассказываю тебе результат и даю ссылку на отчёт. Приёмка остаётся за тобой.

**Нет проверенного отчёта в GitHub — нет подтверждённого результата.**
Статус ВМ, файл на её диске и устный пересказ не заменяют отчёт.
Отчёт об ошибке подтверждает ошибку; успешным расчётом он не считается.

## Что отправляется в GitHub

Код задачи формирует `report/`. Его состав определяется до запуска.

| Часть отчёта | Содержимое |
|---|---|
| `README.md` | Постановка, фактический ответ, сравнение с ожиданием, ограничения и вывод |
| `metrics.json` | Подробные показатели по условиям/группам, объёмы, разброс, экстремумы, ошибки |
| `series.csv`, распределения, таблицы | Динамика, детальные срезы и агрегаты с явно заданным разрешением |
| `checks.json` | Проверки с фактическими значениями, включая провалы |
| Графики, когда нужны | Подписи, единицы, параметры и соответствующие числовые данные |
| `data_manifest.json` | Полные файлы на ВМ, размеры/форматы/хеши, метод отбора и покрытие отчёта |
| Служебный `run.json` | Номер запуска, исходный коммит, завершение, хеши опубликованных файлов |

Гигабайты из `full/` не копируются в GitHub. Публикуется содержимое `report/`;
если выбранный файл превышает лимит, это явная ошибка полноты, а не тихое усечение.
Большой журнал может содержать начало и конец; объём пропуска фиксируется в отчёте.
Агрегаты должны сохранять информацию о редких событиях и крайних значениях.
Метод отбора, количество исходных и опубликованных записей и потери детализации
указываются явно. Это подробный воспроизводимый срез, а не только несколько средних чисел.

Если для вывода не хватает данных, я объясняю, что именно требуется. Доступ к
полным данным на ВМ — после твоего отдельного указания.

## Версии и правки

Код разделяется на удобные для правок файлы и функции. Я меняю нужный участок,
проверяю diff и сохраняю осмысленный небольшой коммит. Исходники, параметры
и ожидания теста имеют версии. В каждом отчёте есть ссылка на выполненный коммит.
Для независимой серии правок можно использовать отдельную ветку и сравнение/PR;
работающий расчёт продолжает использовать свой закреплённый SHA.

## Сбои

- Повтор той же заявки не запускает второй расчёт. Для другой версии нужен новый номер.
- При сбое публикации служба повторяет отправку, сохраняя готовые файлы; расчёт не повторяется.
- Одновременные изменения в GitHub сохраняются. Принудительного перезаписывания ветки нет.
- Перезапуск службы обмена сохраняет очередь. Перезапуск ВМ прерывает сам расчёт;
  его продолжение требует контрольных точек, реализованных в коде задачи.
- Ошибки расчёта, отмена и прерывание должны быть отражены в отчёте GitHub.
- Частичная выгрузка, несовпадение версии или хеша блокируют подтверждение результата.

## Минимальные ограничения первой версии

Один расчёт одновременно. Источник — `run.py` и соседний `config.json`.
Код читает параметры через `Path(__file__).with_name('config.json')`, пишет в текущую папку.
Исходные и выходные файлы: до 512 файлов, до 8 МиБ каждый и до 32 МиБ суммарно.
Скрытые файлы не передаются. `infra/` и `results/` не входят в исходники расчёта.
Пропуски при выгрузке записываются в `export_errors`; такой отчёт не принимается как полный.

## Гейт времени выполнения

До новых запусков фиксируем расчёт ожидаемого времени и допустимый диапазон.
Более быстрое или медленное выполнение за его пределами требует разбора перед
приёмкой. Сверяем также фактические шаги и сохранения. Ожидание очереди и отправку
отчёта учитываем отдельно. Правило: [RUNTIME_GATE.md](RUNTIME_GATE.md).

## Постепенный переезд

ВМ не очищается. Старые проекты, данные, задания и результаты остаются на месте.
Содержимое существующих проектов переносится в GitHub отдельными согласованными этапами.
Новые расчёты получают уникальные номера и не заменяют старые задания.
Во время переезда GitHub постепенно становится интерфейсом к рабочим файлам ВМ.

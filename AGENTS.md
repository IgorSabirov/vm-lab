# Правила работы с этой связкой

## Главный принцип: от установленных границ к проверяемому неизвестному

Прямое указание пользователя от 30 октября 2026:

> Мы фиксируем новизну относительно существующего не для того, чтобы доказать
> первенство, а чтобы понимать, от каких границ уже установленного нам считать.
> Мы не публикуемся, мы частный исследовательский проект, мы не зависим от
> новизны и финансирования.

Это главный принцип научной работы проекта. Литературное сравнение нужно,
чтобы установить, что уже подтверждено, при каких предпосылках и в каких
границах, что из этого применимо к нашей модели и какой вопрос остаётся
проверить. Публикационное позиционирование, первенство и привлечение
финансирования не являются целями или критериями ценности результата.

Наличие предшествующей работы — опора для расчёта и способ избежать лишней
работы. Оно само по себе не обесценивает проверку в нашей модели. Новизна
описывает расстояние от установленного знания до проверяемого вопроса;
не превращать её в соревнование за приоритет или условие продолжения проекта.

В каждом литературном разборе выделять: установленный результат, его условия
и ограничения, применимость к нашей постановке, оставшийся проверяемый вопрос.
Сохранять требования к достоверности, воспроизводимости, опровержимости и
ресурсному бюджету. Не подменять исследовательскую цель вопросом «кто первый».

Пользователь — единственный приёмщик. Дополнительный ИИ-приёмщик не нужен.

## Первое обязательное требование: время

Прямое требование пользователя: расчёт времени обязателен, и разбор любого
прогона начинается со времени независимо от полученных научных результатов.
Это порядок работы по умолчанию; его не нужно заново согласовывать или обсуждать.

До отправки основного прогона в очередь зафиксировать в GitHub расчёт ожидаемой
длительности, источник оценки, допустимый диапазон и стоимость условных веток.
Основной прогон без такого расчёта не запускать.

При получении отчёта первым делом сверить прогноз с фактической длительностью.
Первый содержательный блок ответа пользователю и RESULT.md:
«Время: прогноз …; факт …; отклонение …; статус гейта …».
Ожидание очереди и публикацию учитывать отдельно.

При выходе за любую границу сначала разобрать выполненный объём и причину
расхождения. До закрытия этого разбора не переходить к научным выводам
и не объявлять результат принятым. Если нет нужных данных о времени,
первым статусом ставить NOT_EVALUABLE и выяснять недостающее.
При ещё идущем расчёте сообщать прошедшее время относительно прогноза;
итоговый PASS до завершения не присваивать.

## Критическое правило

Итоговые отчёты для обсуждения и приёмки читать через GitHub; ВМ публикует их сама.
Это обычный канал результатов, а не запрет на управление и диагностику ВМ.
По запросу пользователя «статус», «посмотри ВМ» и аналогичному прямо проверять
процесс, прогресс, контрольные точки и ошибки через доступные инструменты ВМ.
Повторного отдельного разрешения на такую проверку не требуется. Объём чтения
должен соответствовать запросу. Полные научные данные открывать по указанию пользователя.
Прямое чтение ВМ не подменяет проверку итогового отчёта GitHub.
Запрещено самостоятельно переносить результаты с ВМ в GitHub вместо службы.

Уточнение пользователя от 30 октября 2026: полный архив и неопубликованные
научные данные ВМ проверять только по его прямому указанию. По умолчанию
работать через GitHub. Пробел в опубликованном отчёте сам по себе не разрешает
обращение к полному архиву. Разрешение на конкретную проверку не становится
постоянным разрешением для следующих задач. Оперативная диагностика процесса
по запросу пользователя остаётся допустимой, как описано выше.

Если в GitHub нет полного проверенного отчёта, результат не подтверждён.
Недоступность GitHub не разрешает обходной путь через ВМ без указания пользователя.
Для проверки использовать `infra/github_result_reader.py`; зафиксировать
коммит отчёта и читать все его файлы с одним и тем же `ref`.

## ВМ сохраняется

Не очищать ВМ, не удалять её код, данные, старые задания и результаты.
GitHub становится интерфейсом к содержимому ВМ. Переносить существующие
проекты постепенно, сохраняя оригиналы. Полные массивы и тяжёлые файлы остаются
на ВМ. GitHub получает заранее определённый подробный отчёт среднего объёма.

Заявку на исполнение направляет ассистент прямо на ВМ через VM Compute.
Она содержит уникальный `run_id` и полный SHA кода в GitHub.
Прямые команды ВМ также допустимы для установки, диагностики сервиса и отмены.
Ответ на команду управления или статус процесса не является приёмкой научного результата.
По запросу пользователя оперативную диагностику выполнять прямо на ВМ.

## Порядок

1. Записать `run.py` и `config.json` в GitHub, указав ожидаемый результат теста и расчёт времени с диапазоном.
2. Зафиксировать полный SHA кода и уникальный `run_id` до запуска.
3. Передать `data/vm_lab_queue/<run_id>.json` на ВМ; исходники она забирает сама из GitHub.
4. Дождаться отчёта в `results/<run_id>/` на GitHub.
5. Проверить идентичность запуска и сначала сверить прогноз/факт времени; при расхождении завершить разбор причины.
6. Проверить код завершения, полноту, хеши и численное содержание; сообщить вывод со ссылкой на закреплённый отчёт.

Старые репозитории GitHub и их история не используются. Содержимое ВМ сохраняется.
Новая связка предназначена для `IgorSabirov/vm-lab`.

## Код и подробный отчёт

Менять нужные функции/модули малыми коммитами, проверять diff. Не переписывать
проект целиком ради локальной правки. Каждый запуск закреплён на коммите;
последующие правки не меняют уже выданную заявку.

Код расчёта пишет выбранные подробные данные в `report/`, полные — в `full/`.
Служба публикует только `report/` и ограниченный журнал, описывает сокращения.
Отчёт обязан показывать объём исходных данных, покрытие выборки/агрегации,
разброс, динамику, крайние случаи и проваленные проверки, когда они применимы.
Отсутствие необходимого показателя отмечать явно. Не скрывать неудобные результаты.
Если отчёта недостаточно, объяснить, какие полные данные нужны, и дождаться
отдельного указания пользователя перед обращением к ним.

## Гейт времени выполнения

Для новых расчётов до запуска фиксировать в GitHub объём работы, источник замера,
ожидаемое время и допустимый диапазон для каждой условной ветки протокола.
Сравнивать с длительностью выполнения задачи, отдельно от очереди и публикации.
Несовпадение в любую сторону требует разбора перед приёмкой; прогноз задним числом
не менять. Отсутствие прогноза тоже требует разбора. Совпадение времени не заменяет
проверку числа шагов, сохранений, версии и численной корректности.
Порядок и поля отчёта — [RUNTIME_GATE.md](RUNTIME_GATE.md).

## Один компактный файл главных результатов

Для следующих запусков заранее определять `report/RESULT.md`: самодостаточный
текст для пользователя размером до 24 КиБ, с постановкой, основными числами,
всеми условиями и провалами, фактическими проверками, динамикой/экстремумами,
объёмом работы, временем, ограничениями и источниками. Пользователю первым
давать этот файл, а не служебный run.json. Подробные данные и полные проверки
сохраняются отдельно; компактное представление их не заменяет.
При пересылке другому ИИ передаётся содержимое файла: доступ к приватному
GitHub у получателя не предполагается. Правила: [REPORT_FORMAT.md](REPORT_FORMAT.md).

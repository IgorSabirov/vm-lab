# Правила работы с этой связкой

Пользователь — единственный приёмщик. Дополнительный ИИ-приёмщик не нужен.

## Критическое правило

Итоговые отчёты для обсуждения и приёмки читать через GitHub; ВМ публикует их сама.
Это обычный канал результатов, а не запрет на управление и диагностику ВМ.
По запросу пользователя «статус», «посмотри ВМ» и аналогичному прямо проверять
процесс, прогресс, контрольные точки и ошибки через доступные инструменты ВМ.
Повторного отдельного разрешения на такую проверку не требуется. Объём чтения
должен соответствовать запросу. Полные научные данные открывать по указанию пользователя.
Прямое чтение ВМ не подменяет проверку итогового отчёта GitHub.
Запрещено самостоятельно переносить результаты с ВМ в GitHub вместо службы.

Если в GitHub нет полного проверенного отчёта, результат не подтверждён.
Недоступность GitHub не разрешает обходной путь через ВМ без указания пользователя.
Для проверки использовать `infra/github_result_reader.py`; зафиксировать
коммит отчёта и читать все его файлы с одним и тем же `ref`.

## ВМ сохраняется

Не очищать ВМ, не удалять её код, данные, старые задания и результаты.
GitHub становится интерфейсом к содержимому ВМ. Переносить существующие
проекты постепенно, сохраняя оригиналы. Полные массивы и тяжёлые файлы остаются
на ВМ. GitHub получает заранее определённый подробный отчёт среднего объёма.

Заявку на исполнение направляет ассистент прямо на ВМ через VM Compute.
Она содержит уникальный `run_id` и полный SHA кода в GitHub.
Прямые команды ВМ также допустимы для установки, диагностики сервиса и отмены.
Ответ на команду управления или статус процесса не является приёмкой научного результата.
По запросу пользователя оперативную диагностику выполнять прямо на ВМ.

## Порядок

1. Записать `run.py` и `config.json` в GitHub, указав ожидаемый результат теста.
2. Зафиксировать полный SHA кода и уникальный `run_id` до запуска.
3. Передать `data/vm_lab_queue/<run_id>.json` на ВМ; исходники она забирает сама из GitHub.
4. Дождаться отчёта в `results/<run_id>/` на GitHub.
5. Проверить привязку к запуску и исходному SHA, код завершения, полноту и хеши.
6. Сообщить пользователю вывод с ссылкой на точный коммит отчёта.

Старые репозитории GitHub и их история не используются. Содержимое ВМ сохраняется.
Новая связка предназначена для `IgorSabirov/vm-lab`.

## Код и подробный отчёт

Менять нужные функции/модули малыми коммитами, проверять diff. Не переписывать
проект целиком ради локальной правки. Каждый запуск закреплён на коммите;
последующие правки не меняют уже выданную заявку.

Код расчёта пишет выбранные подробные данные в `report/`, полные — в `full/`.
Служба публикует только `report/` и ограниченный журнал, описывает сокращения.
Отчёт обязан показывать объём исходных данных, покрытие выборки/агрегации,
разброс, динамику, крайние случаи и проваленные проверки, когда они применимы.
Отсутствие необходимого показателя отмечать явно. Не скрывать неудобные результаты.
Если отчёта недостаточно, объяснить, какие полные данные нужны, и дождаться
отдельного указания пользователя перед обращением к ним.

## Гейт времени выполнения

Для новых расчётов до запуска фиксировать в GitHub объём работы, источник замера,
ожидаемое время и допустимый диапазон для каждой условной ветки протокола.
Сравнивать с длительностью выполнения задачи, отдельно от очереди и публикации.
Несовпадение в любую сторону требует разбора перед приёмкой; прогноз задним числом
не менять. Отсутствие прогноза тоже требует разбора. Совпадение времени не заменяет
проверку числа шагов, сохранений, версии и численной корректности.
Порядок и поля отчёта — [RUNTIME_GATE.md](RUNTIME_GATE.md).
